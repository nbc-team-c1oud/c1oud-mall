## idempotency Design Topology

# dempotency Design Topology

> 이 문서는 **시스템 가치(멱등성)를 어떻게 설계할 것인가**를 위상 관점에서 정의한다.
`system-value-topology` Tier 1 가치 *멱등성*의 구체 설계 영역이다.
멱등성은 정합성을 지키기 위한 수단 — `consistency-design-topology`와 상호 참조 지점이 많다.
Layer 1에 속한다. 멱등 지점 카탈로그(3-2)만 Layer 2적으로 진화.
구체 어휘(클래스명·API 경로·구체 키 형식)는 의도적으로 배제했다.
>

---

## 0. One-Line Declaration

> **모든 외부 진입점과 비결정 사이드 이펙트 작업은 멱등하다. 각 멱등 지점은 *키 출처 · 감지 메커니즘 · 응답 정책*의 세 차원에서 명시적으로 결정된다. 본질적으로 멱등이거나 멱등이 불가능한 영역은 별도로 식별되어 다른 보장을 받는다.**
>

멱등성은 *추가하는 기능*이 아니라 *외부와 만나는 모든 표면의 기본 속성*이다. 결제 시스템에서 멱등성이 빠진 진입점은 사고가 발생하는 자리.

---

## 1. 멱등성 결정의 흐름

**다이어그램 읽는 법**

- 각 멱등 지점은 4개 차원에서 *하나의 경로*를 선택
- 가장 강한 경로: 사용자 API → 서버 채번 → 유니크+상태 이중 → Idempotent response
- 가장 약한 경로: 진입점이 멱등 검사를 우회하면 *경로 자체가 없음*

---

## 2. 멱등성 정의와 분류

### 2-1. 본 시스템의 멱등성 정의 (A-1)

**수학적 정의** (이론): `f(f(x)) = f(x)`. 같은 입력에 대해 함수 호출 횟수와 무관하게 같은 결과.

**본 시스템 정의** (실용): **같은 의도의 요청을 N회 수행해도, 시스템 상태와 응답이 1회 수행한 것과 같다.**

핵심 차이:

- "같은 요청 바이트"가 아니라 *"같은 의도"*. 키로 동일성을 판단.
- "같은 결과"는 응답까지 포함 — 두 번째 호출에 다른 응답이 가면 클라이언트가 다른 상태로 인식.
- *부수효과*까지 1회 = N회. 외부 호출·이벤트 발행·로그도 동일.

### 2-2. 멱등 / 비멱등 / 본질적 멱등의 식별 (A-2)

| 분류 | 정의 | 본 프로젝트 예 |
| --- | --- | --- |
| **본질적 멱등 (Naturally idempotent)** | 작업 자체의 성질로 멱등. 추가 보장 메커니즘 불필요. | 단순 조회 GET, 상태를 *그 값으로* 설정 (이미 그 값이면 변화 없음) |
| **설계적 멱등 (Designed idempotent)** | 본질적으론 비멱등이지만 *키 기반 중복 감지*로 멱등화. 본 문서의 주된 대상. | 결제 확정, Webhook 처리, 환불 요청, 구독 청구 |
| **본질적 비멱등 (Naturally non-idempotent)** | 작업 자체가 매번 부수효과 누적. 멱등화 불가능. | 외부 알림 발송, 외부 정산 통지, 로그 기록 |

**원칙**

- 본질적 멱등은 *별도 보장 없이* OK. 메커니즘 안 둠.
- 설계적 멱등은 *모든 차원에서 명시적 결정*. 본 문서의 핵심.
- 본질적 비멱등은 *멱등 영역과 분리*. 보통 비동기 이벤트 처리로 격리 + at-least-once 수용.

## 3. 멱등성 요구 지점의 식별

### 3-1. Inbound trigger별 멱등성 요구 수준 (B-1)

| Trigger | 멱등 필수성 | 이유 |
| --- | --- | --- |
| **사용자 API (상태 변경)** | ✅ 필수 | 더블 클릭·네트워크 재전송·페이지 새로고침. 사용자가 *모르고* 중복 보냄. |
| **Webhook (외부 → 내부)** | ✅ 필수 | 외부 시스템이 *의도적으로* 재시도. 순서도 뒤바뀔 수 있음. |
| **Scheduler (정기 트리거)** | ✅ 필수 | 두 인스턴스가 동시 실행되거나, 재실행 시 중복 가능. |
| **내부 비동기 이벤트** | ✅ 필수 | At-least-once 전제. 메시지 중복 자연 발생. |
| **사용자 API (조회)** | ❌ 불필요 | 본질적 멱등. |
| **내부 동기 호출** | 🔶 권장 | 직접적 중복은 드물지만, 호출자 재시도 시 안전성. |

### 3-2. 본 프로젝트의 멱등 작업 카탈로그 (B-2) — **본 문서의 중심**

> 본 프로젝트의 *모든 설계적 멱등 작업*을 전수 조사. 새 진입점 추가 시 이 표 갱신 필수 (12-1 PR 게이트). -Live 문서 가능성
>

| # | 멱등 지점 | 진입점 | 키 출처 | 감지 메커니즘 | 응답 정책 | 윈도우 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | **결제 확정** | Confirm API | 서버 채번 `portonePaymentId` | 유니크 + 상태 이중 | Idempotent response | 영구 |
| 2 | **Webhook 결제 통지** | Webhook | 외부 제공 `portonePaymentId` | 상태 기반 | Silent OK (200) | 영구 |
| 3 | **주문 생성** | Order Create API | 서버 채번 (주문 시 발급) | 유니크 (주문 ID) | Idempotent response 또는 Explicit reject | 영구 |
| 4 | **주문 취소** | Order Cancel API | 비즈니스 식별자 (주문 ID + 상태) | 상태 기반 | Silent OK | 영구 |
| 5 | **환불 요청** | Refund API | 비즈니스 식별자 (주문 ID + 환불 대상 주문상품 ID + 수량) | 상태 기반 (잔여 환불 가능 수량) | Explicit reject (초과 시) | 영구 |
| 6 | **회원가입** | Sign-up API | 비즈니스 식별자 (이메일) | DB 유니크 | Explicit reject | 영구 |
| 7 | **장바구니 상품 담기** | Cart API | 비즈니스 식별자 (회원 ID + 상품 ID) | 상태 기반 (수량 합산) | Idempotent response | 영구 |
| 8 | **구독 청구** (도전) | Scheduler | 비즈니스 식별자 (구독 ID + 청구 주기) | DB 유니크 | Silent skip | 영구 |
| 9 | **구독 시작** (도전) | Subscription Start API | 비즈니스 식별자 (회원 ID + 요금제) | DB 유니크 또는 상태 기반 | Explicit reject (이미 활성 구독 존재) | 영구 |
| 10 | **구독 해지** (도전) | Subscription Cancel API | 상태 기반 (이미 해지면 OK) | 상태 기반 | Silent OK | 영구 |

**관찰**

- *대부분의 멱등 지점이 "영구" 윈도우*. 본 프로젝트는 비즈니스 식별자나 도메인 키가 영구 보존됨.
- *상태 기반과 키 기반이 약 50:50*. 어느 게 더 자연스러운지 작업의 본성에 따름 (9장 참조).
- *Webhook만 Silent OK*. 다른 진입점은 명시적 응답.

### 3-3. 본질적으로 멱등인 작업 (B-3)

별도 메커니즘 없이 안전한 영역. 멱등성 비용을 안 치러도 됨.

- **모든 GET 조회 API** — 부수효과 없음.
- **상태를 *특정 값으로* 직접 설정**: 예: "구독 상태를 *해지*로 설정". 이미 해지면 변화 없음.
- **append-only 로그/audit 기록 *중복이 의미 있는 경우***: 같은 요청을 2번 받아 2번 로그가 남는 게* 원하는 동작*인 경우. (다만 결제 도메인에선 거의 없음 — 결제 로그가 두 번 남으면 사고)
- **Idempotent SQL UPDATE**: `UPDATE x SET status = 'A' WHERE status = 'B'`. WHERE 조건이 *이미 변경됨*을 자연스럽게 거부.

**원칙**: 본질적 멱등을 *발견*하면 별도 멱등 메커니즘을 *추가하지 않는다.* 코드 단순성 보존.

## 4. 멱등성 키의 출처와 책임

### 4-1. 키 출처 분류 (C-1)

| 출처 | 정의 | 신뢰 수준 | 책임 위치 |
| --- | --- | --- | --- |
| **서버 채번** | 우리 시스템이 *최초 요청 시* 발급하고 클라이언트에 반환 | 🟢 가장 높음 | 우리 |
| **외부 시스템 제공** | 외부 시스템이 발급한 키를 그대로 사용 | 🟢 위변조 어려움 + 🟡 우리가 발급 안 함 | 외부 + 우리 |
| **비즈니스 식별자** | 이미 존재하는 의미 있는 ID 조합 (이메일, 주문ID+상품ID 등) | 🟢 위변조 어려움 (의미 있는 데이터) | 우리 |
| **클라이언트 제공 (Idempotency-Key 헤더)** | 클라이언트가 매 요청에 키 생성 | 🟡 위변조 가능 / UUID 충돌 가능 | 클라이언트 + 우리 |

**원칙**

- 가능하면 *서버 채번 또는 비즈니스 식별자* 우선.
- 클라이언트 제공 키는 *최후 수단*. 본 프로젝트에선 채택 안 함 (4-2 참조).
- 외부 키는 *그대로 사용*하되, *우리 도메인의 멱등 키 역할*을 한다는 점을 명시.

### 4-2. 본 프로젝트 각 지점의 키 출처 결정 (C-2)

3-2의 매트릭스를 키 출처 관점에서 재정렬.

**서버 채번**

- 결제 확정: `portonePaymentId` — *주문 생성 시점*에 채번해 결제 사전 등록과 함께 저장. PortOne에 보낼 외부 키이자 *우리 멱등 키의 역할도 겸함*.
- 주문 생성: 주문 ID — DB AUTO_INCREMENT

**외부 제공**

- Webhook: PortOne이 보낸 `paymentId`. 우리가 발급한 `portonePaymentId`와 같은 값 (8-3 참조).

**비즈니스 식별자**

- 회원가입: 이메일.
- 장바구니 담기: (회원 ID, 상품 ID) 조합.
- 환불 요청: (주문 ID, 환불 대상 주문상품 ID, 수량) 조합.
- 구독 청구: (구독 ID, 청구 주기) 조합.

**클라이언트 제공**: **본 프로젝트 채택 안 함.**

- 이유: 신뢰 수준 낮음. UUID 충돌·위변조 가능성. 별도 검증 비용.
- 대안: 모든 사용자 API는 서버 채번 또는 비즈니스 식별자로 대체 가능.
- 미래 가능성: 고빈도 API나 외부 파트너 API 도입 시 검토.

### 4-3. 키의 신뢰 수준과 검증 (C-3)

키 출처에 따라 검증 강도가 다름.

| 키 출처 | 추가 검증 |
| --- | --- |
| 서버 채번 | 검증 불필요. 우리가 발급. |
| 외부 제공 (Webhook) | **위변조 방지를 위해 외부 서명 검증** (HMAC). 키 자체가 위변조되었으면 키 자체를 신뢰 못 함. |
| 비즈니스 식별자 | 식별자가 *현재 요청자에 속하는지* 소유권 검증. (예: 환불 요청 시 주문이 요청자 소유인지) |
| 클라이언트 제공 (채택 안 함) | (해당 없음) |
|  |  |

**Webhook 키의 특수성**

- PortOne `paymentId`는 외부 제공이지만, *우리가 발급한 `portonePaymentId`와 같은 값*.
- 따라서 키 자체는 우리가 생성한 것 — 신뢰할 수 있음.
- 그러나 *그 키를 누가 들고 왔는지*는 검증해야 함 — HMAC 서명 검증.
- 검증 후엔 *그 키로 PortOne에 재조회*. Webhook 페이로드의 다른 필드는 신뢰하지 않음.

## 5. 중복 감지 메커니즘

### 5-1. 감지 메커니즘 분류와 신뢰성 등급 (D-1, D-3)

| 메커니즘 | 등급 | Race 내성 | 비용 | 설명 |
| --- | --- | --- | --- | --- |
| **DB 유니크 제약** | **S** | ✅ 완전 | 낮음 | DB가 직접 보장. 동시 INSERT 시 한 쪽만 성공. |
| **DB 유니크 + 사전 조회 이중** | **S+** | ✅ 완전 | 중간 | 사전 조회로 빠른 거부 + 유니크가 race 방어. |
| **분산 락 + 상태 검증** | **A** | ✅ 완전 | 높음 | 락 안에서 상태 확인 → 결정. 다중 인스턴스에 유용. |
| **트랜잭션 + 비관적 락 + 상태 검증** | **A** | ✅ 완전 | 높음 | `SELECT FOR UPDATE` + 상태 확인. 단일 인스턴스에서 충분. |
| **상태 기반 (단순)** | **B** | 🟡 race vulnerable | 낮음 | "상태가 이미 그 값이면 패스". 동시 진입 시 둘 다 통과 가능. |
| **Application 메모리 캐시** | **C** | ❌ 인스턴스간 무용 | 매우 낮음 | 단일 인스턴스에서만 부분 유효. *본 프로젝트 채택 안 함*. |

**원칙**: *Race-critical 영역은 반드시 S 또는 A급*. B급은 race가 비즈니스적으로 OK일 때만.

### 5-2. 각 멱등 지점의 메커니즘 선택 (D-2)

3-2 매트릭스를 메커니즘 관점에서 정당화.

| 멱등 지점 | 메커니즘 | 등급 | 이유 |
| --- | --- | --- | --- |
| **결제 확정** | DB 유니크(`portonePaymentId`) + 사전 조회 + 상태 검증 | S+ | 금융 critical. 동시 진입 가능 (Webhook + Confirm). 최강 보장. |
| **Webhook 결제 통지** | 상태 기반 (결제 상태 == 완료면 패스) | B → A | 상태 기반 자체는 B급이지만, *결제 확정 zone의 트랜잭션 + 비관적 락*과 결합되어 A급으로 격상. |
| **주문 생성** | DB 유니크 (주문 ID는 AUTO_INC) | S | 주문 ID 자체가 유니크. 사용자 식별자 + 시간 등으로 중복 방지 가능. |
| **환불 요청** | 트랜잭션 + 잔여 환불 가능 수량 검증 | A | 비관적 락으로 환불 대상 주문상품 잠금 후 잔여 수량 검증. |
| **회원가입** | DB 유니크 (이메일) | S | 가장 단순한 케이스. |
| **장바구니 담기** | 비관적 락 + 수량 합산 | A | "수량을 합산"하는 행위 자체가 멱등성 정의의 변형. *완전한 멱등은 아님* — 같은 요청 2번 = 수량 2배. 비즈니스 정의상 OK. |
| **구독 청구 (도전)** | DB 유니크 (구독 ID + 청구 주기) | S | Scheduler 중복 실행 방어. UNIQUE 충돌 시 자연스럽게 skip. |
| **구독 시작 (도전)** | 상태 검증 (활성 구독 존재 여부) | A | 트랜잭션 + 비관적 락 결합. |
| **구독 해지 (도전)** | 상태 기반 (이미 해지면 OK) | B | 가역 작업 아님 + 비즈니스 critical 아님. B급으로 충분. |

**중요 패턴**: Webhook과 결제 확정 API는 *같은 자원*을 만지므로, 각각 다른 메커니즘으로 보이지만 *공유 도메인 서비스*에서 같은 트랜잭션·같은 락으로 직렬화됨 (consistency 7-3 참조).

## 6. 중복 시 응답 정책

### 6-1. 응답 정책 분류 (E-1)

| 정책 | 의미 | 응답 코드 | 사용처 |
| --- | --- | --- | --- |
| **Idempotent response** | 첫 처리와 *동일한 결과* 반환 | 200 / 201 (동일) | 사용자 API에서 안전한 재시도 보장 |
| **Silent OK** | 처리 안 하고 성공 응답만 | 200 | Webhook (외부 재시도 막기) |
| **Explicit reject** | "이미 처리됨" 명시적 거부 | 409 Conflict | 사용자가 인지할 수 있어야 하는 경우 |
| **Silent skip** | 처리 안 하고 다음 트리거 대기 | (응답 없음) | Scheduler 중복 실행 시 |

### 6-2. 각 진입점의 응답 정책 결정 (E-2)

**Idempotent response** (첫 처리와 동일 결과)

- 결제 확정: 두 번째 호출도 첫 결제 결과와 동일한 응답.
- 장바구니 담기: 수량 합산이 자연스러운 동작.

**Silent OK** (외부 재시도 막기)

- Webhook 결제 통지: PortOne이 *200을 받을 때까지 재시도*. 이미 처리된 경우도 200 반환.

**Explicit reject** (사용자에게 알림)

- 회원가입: "이미 가입된 이메일" — 사용자가 알아야 함.
- 환불 요청 잔여 초과: "환불 가능 수량 초과" — 사용자 인지 필요.
- 구독 시작 시 활성 구독 존재: "이미 활성 구독" — 명확한 거부.

**Silent skip** (재실행 방지, 다음 주기)

- 구독 청구 Scheduler: UNIQUE 충돌 시 그냥 skip. 다음 청구 주기까지 대기.

### 6-3. 첫 처리와 동일한 응답 보장 여부 (E-3)

**Idempotent response 채택 시의 정밀도 결정**

| 보장 수준 | 의미 | 본 프로젝트 채택 |
| --- | --- | --- |
| **완전 동일** | 응답 바이트가 정확히 일치 | ❌ 과잉 |
| **의미 동일** | 결과 데이터가 동일 (타임스탬프 등 메타 제외) | ✅ 본 프로젝트 표준 |
| **상태 동일** | "처리 완료" 메시지만 동일 | 🔶 부분 채택 |

**결제 확정의 응답 정책**: *의미 동일* — 결제 완료 정보(금액·상태·시각)는 동일. 응답 헤더의 타임스탬프 같은 메타는 다름.

**환불 요청의 응답 정책**: *상태 동일* — "이 환불은 이미 처리됨"으로 거부 (Explicit reject로 갈 수도 있음 — 비즈니스 결정).

## 7. 멱등성 보장 윈도우

### 7-1. 윈도우 종류 분류 (F-1)

| 윈도우 | 의미 | 트레이드오프 |
| --- | --- | --- |
| **영구** | 키를 영구 보존. 어떤 시점의 중복도 감지. | 저장 비용 누적 / 모든 시점 안전 |
| **시간 제한 (N일)** | N일 후 키 만료. 그 후 도착한 중복은 새 요청으로 처리. | 저장 비용 절감 / 매우 늦은 중복은 새 처리 |
| **세션 제한** | 사용자 세션 기간만 유효. | 단순 / 세션 외 중복 미감지 |

### 7-2. 본 프로젝트의 윈도우 정책 (F-2)

**원칙**: 본 프로젝트는 **모든 멱등 지점이 영구 윈도우.**

**이유**

- 키 자체가 비즈니스 데이터 (`portonePaymentId`, 주문 ID, 이메일 등). 영구 보존되어야 함.
- 결제 도메인에서 *매우 늦은 중복*도 사고 가능 (예: PortOne의 늦은 Webhook 재시도).
- 저장 비용 절감보다 정확성이 우선.

**예외 검토**

- Webhook 키 만료를 N일로 둘 수도 있음. PortOne이 N일 이상 후에 같은 Webhook을 재전송하는 경우가 없으면 OK.
- *현재 채택 안 함*. 보수적으로 영구 보존.

## 8. 멱등성과 트랜잭션의 결합 — Consistency와의 결합점

### 8-1. 멱등 검사의 트랜잭션 위치 (G-1)

멱등 검사가 트랜잭션의 *어느 시점*에 일어나는가.

| 위치 | 메커니즘 | 적용 |
| --- | --- | --- |
| **트랜잭션 진입 *전*** | 사전 조회 (read-only) | 빠른 거부 (성능). Race 가능성 있음. |
| **트랜잭션 진입 *직후*** | 트랜잭션 안 첫 쿼리 | DB 일관성 보장. |
| **DB 유니크 제약 (INSERT 시점)** | DB가 직접 | Race-safe. |
| **트랜잭션 *커밋 시점*** | DB가 제약 검증 | 가장 늦은 시점. |

**본 프로젝트 표준 패턴**: *사전 조회 + DB 유니크 제약*의 이중 보장.

`1. (트랜잭션 전) 사전 조회로 빠른 거부 — race 발생 시 통과 가능
2. (트랜잭션 안) INSERT 시도
3. (DB) 유니크 제약이 race-safe 보장 — 충돌 시 예외
4. 예외를 잡아 "이미 처리됨"으로 정상 응답`

이 패턴이 *S+ 등급*인 이유: 사전 조회로 99% 빠르게 거부 + 유니크 제약으로 100% 보장.

### 8-2. 외부 호출과 멱등성 (G-2) — **Consistency 7-1과 직결**

외부 호출 시 멱등성 보장의 핵심 패턴.

**원칙**: 외부 호출은 트랜잭션 *밖*에서 (Consistency 7-1). 그러므로 멱등성 검사는 *외부 호출 전·후 모두* 필요.

`[외부 호출 전 멱등 검사]
  ↓ (통과)
[외부 호출]
  ↓ (성공 또는 응답 모름)
[DB 트랜잭션 진입]
[멱등 검사 재확인 — 트랜잭션 안 + 락]
  ↓ (재확인 통과)
[상태 변경 + 외부 결과 기록]
[커밋]`

**왜 두 번 검사하는가**

- 외부 호출 전 검사: 외부 호출 비용 절감 (이미 처리된 거 또 호출 안 함)
- 트랜잭션 안 재확인: 외부 호출 동안 *다른 진입점*이 동시에 처리했을 수 있음 (Webhook + Confirm 동시 도달)

**외부 호출이 *멱등성 키를 자체적으로 보장*하는 경우**: PortOne은 `paymentId`로 멱등 보장. 우리가 같은 `paymentId`로 두 번 호출해도 두 번 결제되지 않음. *우리 시스템 멱등성*과 *PortOne 멱등성*은 두 층의 방어.

### 8-3. 부분 실패 시 멱등성 보존 (G-3)

**시나리오**: 멱등 작업 처리 도중 실패. 어디까지 진행됐는지 모름. 재시도 시 어떻게 되는가.

**원칙**: 멱등 작업은 *부분 진행 상태*를 가지지 않는다. 트랜잭션으로 atomic 보장.

**구체 패턴**

| 실패 시점 | 결과 | 재시도 시 동작 |
| --- | --- | --- |
| 트랜잭션 안 실패 | 자동 롤백. 멱등 키도 INSERT 안 됨. | 새 요청으로 처리. 정상. |
| DB 커밋 후 외부 호출 실패 | DB는 커밋됨. 외부는 모름. | 멱등 키 이미 존재 → "이미 처리됨" 응답. 외부 보상은 별도 처리. |
| 외부 호출 후 DB 커밋 전 실패 | 외부는 처리됨. DB는 안 됨. | 멱등 키 없음 → 재처리 시도. 외부 멱등 보장(PortOne)에 의존. |

**가장 어려운 케이스**: *외부 호출 후 DB 커밋 전 실패*. 외부와 우리가 불일치. *외부 멱등 보장이 critical*. PortOne의 `paymentId` 멱등이 이걸 받쳐줌.

## 9. 외부 시스템 멱등성 의존

### 9-1. PortOne의 멱등 보장 분석 (H-1)

**PortOne이 자체적으로 보장하는 영역**

- `paymentId`(우리가 보낸 `portonePaymentId`) 기반 멱등. 같은 `paymentId`로 결제 요청 시 두 번 결제되지 않음.
- 같은 `paymentId`로 결제 취소 요청 시 두 번 취소되지 않음.

**PortOne이 보장하지 *않는* 영역**

- *우리 시스템의* 내부 상태 일관성.
- *우리 시스템의* 부수 처리 (포인트 적립, 멤버십 갱신 등) 멱등성.
- *우리 시스템의* 트랜잭션 경계.

### 9-2. 우리가 추가로 보장해야 하는 부분 (H-2)

PortOne 보장 외 영역의 우리 책임.

1. **결제 확정의 우리 측 멱등성**: PortOne이 한 번 결제했어도, 우리 시스템에서 *결제 확정 처리*는 두 번 실행되면 안 됨 (이중 적립·이중 장바구니 초기화 등).
2. **Webhook과 Confirm API의 양방향 멱등성**: 같은 결제에 대해 두 진입점이 모두 처리 시도. 둘 중 한 번만 *실제 처리* 일어나야 함.
3. **환불 처리의 우리 측 멱등성**: PortOne 취소가 멱등이라도, *환불 기록 자체*가 두 번 남으면 안 됨.
4. **구독 정기 결제의 우리 측 멱등성**: PortOne 빌링키 결제가 멱등이라도, *우리 청구 기록*은 한 번만.

**규칙**: *외부 보장에 의존하지 말고 항상 우리 보장을 추가.* 외부 보장은 *비용 절감*이지 *우리 책임 대체*가 아님.

### 9-3. 외부 키와 내부 키의 관계 (H-3)

`portonePaymentId`는 *외부 키이자 내부 멱등 키*의 이중 역할.

**이중 역할의 함의**

- *발급은 우리가* (주문 생성 시점에 사전 채번).
- *전달은 양방향* (우리 → PortOne, PortOne → 우리 via Webhook).
- *의미는 단일* — 한 결제 의도의 식별자.

**왜 이렇게 설계하는가**

- 외부 키를 따로 두고 내부 멱등 키를 또 두면 *매핑 비용*과 *불일치 위험* 발생.
- 한 키로 통합하면 단순.
- 단점 인정: 외부 키 형식에 우리 멱등 정책이 묶임. PortOne의 ID 형식이 바뀌면 우리도 영향.

**일반화**: *외부 시스템과 통신하는 멱등 지점*에서는 *외부 시스템이 키를 식별 가능*해야 함. 따로 두는 비용보다 통합 비용이 작음.

## 10. 상태 기반 vs 키 기반 멱등성

### 10-1. 두 접근의 차이 (I-1)

| 접근 | 질문 | 메커니즘 | 강점 | 약점 |
| --- | --- | --- | --- | --- |
| **키 기반** | "이 키를 본 적 있어?" | DB 유니크 조회 / INSERT | Race-safe (S급 가능). 명시적. | 키 출처가 필요. 키 위변조 위험. |
| **상태 기반** | "이 자원이 이미 그 상태인가?" | 자원 상태 조회 + 조건 분기 | 키 불필요. 자연스러움. | Race vulnerable (B급). 자원의 상태 표현이 명확해야. |

### 10-2. 본 프로젝트에서의 적용 분기 (I-2)

**키 기반이 자연스러운 경우**

- 신규 자원 생성 (회원가입·주문 생성·결제 사전 등록).
- 식별자가 자연스럽게 존재 (이메일·주문 ID 등).
- DB 유니크 제약으로 단순 강제.

**상태 기반이 자연스러운 경우**

- 기존 자원의 *상태 전이* (주문 취소·결제 확정·구독 해지).
- 상태가 명시적으로 정의됨 (Enum 등).
- 멱등 키를 따로 발급하기 부자연스러움.

**이중 보장이 자연스러운 경우**

- Race-critical 영역 + 자원 상태도 명확한 경우.
- 결제 확정이 대표 — *키 기반*으로 race 차단 + *상태 기반*으로 의미 검증.

**판단 기준**: 자원의 *상태 표현*이 명확하고 *race가 비즈니스적으로 OK*면 상태 기반. *race가 critical*하거나 *상태가 모호*하면 키 기반. 둘 다면 이중 보장.

## 11. 멱등성 위반의 감지

### 11-1. 중복 처리 발생 신호 (J-1)

멱등성이 깨졌을 때 어떻게 알 수 있는가.

**로그/메트릭 신호**

- 멱등 키 충돌 횟수 갑자기 증가 (정상 동작이지만 패턴 변화는 신호)
- 같은 `portonePaymentId`로 *처리 완료 로그*가 두 번 남음 (이건 확실한 위반)
- 한 주문에 환불 기록이 *예상보다 많음*
- 포인트 잔액 ≠ 거래 내역 합계 (Consistency 측 위반이지만 멱등 위반이 원인일 수 있음)

**감지 메커니즘**

- 즉시: DB 제약 위반 예외 (정상 동작 — 멱등이 작동한 증거)
- 지연: 정기 reconciliation (잔액 ↔ 원장 대조)
- 지연: 메트릭 대시보드 (충돌률·중복률)

**현재 단계 적용**: 즉시 감지(DB 제약)만 필수. 지연 감지는 운영 시작 후.

## 12. 진화 정책

### 12-1. 새 진입점 추가 시 멱등성 정책 결정 절차 (K-1)

**모든 새 진입점이 PR 게이트를 통과해야 함.**

- [ ]  이 진입점이 *상태를 변경*하는가? (조회면 멱등 불필요)
- [ ]  *본질적 멱등*인가? (상태 직접 설정 등) — YES면 별도 메커니즘 불필요
- [ ]  본질적 멱등이 아니면 멱등 작업 카탈로그(3-2)에 추가:
    - 키 출처는 무엇인가? (4-1 분류 중 선택)
    - 감지 메커니즘은 무엇인가? (5-1 분류 중 선택)
    - 응답 정책은 무엇인가? (6-1 분류 중 선택)
    - 윈도우는 무엇인가? (7-1 분류 중 선택)
- [ ]  외부 시스템과 통신하는가? PortOne 멱등 보장에 우리 멱등성을 추가했는가? (9-2)
- [ ]  트랜잭션 위치와의 결합을 점검했는가? (8장)

이 체크리스트를 통과하지 않으면 *멱등성이 누락된 진입점*이 발생. 결제 도메인에선 즉시 사고로 이어짐.

## 13. 안티패턴

### 13-1. "사용자가 한 번만 누를 거다" 가정 (L-1)

**증상**: 더블 클릭·페이지 새로고침·네트워크 재전송을 고려하지 않은 코드.

**예**: 결제 버튼 클릭 시 "결제 처리 중" 화면 + 재클릭 비활성화. 그러나 *백엔드에는 멱등성 없음*.

**문제**: 프론트엔드 보호는 우회 가능. 네트워크 재전송은 프론트엔드가 인지 못 함.

**대응**: *백엔드 멱등성이 진실의 출처*. 프론트엔드 보호는 UX 보조이지 정합성 보호 수단 아님.

### 13-2. 중복 처리되어도 정합성 안 깨질 거란 낙관 (L-2)

**증상**: "이 작업은 두 번 처리되어도 별 일 없을 것"이라는 검증되지 않은 가정.

**예**: 포인트 적립이 두 번 일어나도 *큰 액수는 아니니 OK*라는 판단.

**문제**: 사용자가 알면 신뢰 무너짐. 정산 시 발견되면 더 큰 사고. 누적되면 큰 액수.

**대응**: 모든 *상태 변경 진입점*에 멱등성 의식적 검토. "두 번 처리되어도 OK"라는 결론도 *명시적 결정*으로 박제 (왜 OK인지 근거 포함).

### 13-3. 멱등 키의 의미 변질 (L-3)

**증상**: 같은 멱등 키가 *다른 의미*로 재사용됨.

**예 1**: 사용자 A가 결제 요청 → `portonePaymentId` 발급 → 결제 실패 → 같은 `portonePaymentId`로 다른 주문에 사용.

**예 2**: 환불 키로 (주문 ID + 상품 ID) 조합 사용 → 같은 상품을 부분 환불 후 재구매 → 새 결제에 같은 키 → 이전 환불과 충돌.

**문제**: 키가 어느 작업을 가리키는지 모호해짐. 디버깅 불가능.

**대응**:

- *멱등 키는 한 의도에 영구 종속*. 재사용 금지.
- 비즈니스 식별자 사용 시 *시간 차원 포함* 검토 (구독 ID + 청구 주기처럼).
- 실패한 작업에 사용된 키도 *재사용 안 함*. 새 키 발급.

### 13-4. 자기 키로 자기 키 검증 (L-4)

**증상**: DB에 키를 저장하면서 *그 키를 다시 검증*하는 무의미한 코드.

**예**: 결제 요청 시 *클라이언트가 키를 보냄* → 서버가 키를 DB에 저장 → 다음 요청 시 *그 키를 다시 보내달라고* 클라이언트에 요구 → 그게 일치하는지 검사.

**문제**: 키 출처가 *클라이언트*인데 서버에서 *저장 후 재검증*. 출처 신뢰 수준에 모순.

**대응**:

- 키 출처가 클라이언트면 *위변조 가능성*을 의식. 추가 검증(서명 등) 필요.
- 키 출처가 서버 채번이면 *클라이언트가 보낸 키를 신뢰*하지만, 서버 발급 기록과 매칭만 확인.
- 본 프로젝트는 클라이언트 제공 키를 채택하지 않으므로 이 안티패턴 자체가 드묾.

### 13-5. 멱등성 윈도우 외부 도착의 silent 처리 (L-5)

**증상**: 시간 제한 윈도우를 두었는데, 윈도우 외부에 도착한 중복을 *silent로 새 요청*처럼 처리.

**예**: 멱등 키 7일 보관 → 8일째 PortOne이 늦은 Webhook 재시도 → 우리 시스템에 키 기록 없음 → 새 결제처럼 처리 → 이중 적립.

**문제**: 윈도우 자체의 존재가 안티패턴 표면이 됨. 디버깅 어려움.

**대응**:

- 본 프로젝트는 *영구 윈도우* 채택. 이 안티패턴 회피.
- 시간 제한 윈도우를 둘 거면 *윈도우 외부 도착 시 명시적 로깅·알림*. silent 금지.

## 16. 변경 정책

이 문서는 Layer 1이다. 멱등성 4차원 분류와 핵심 원칙은 거의 변하지 않음. 멱등 지점 카탈로그(3-2)만 Layer 2적으로 진화.

- **자유롭게 변경 가능**: 자가 점검 질문, 다이어그램 시각 표현
- **PR 게이트 통과 필요**: 멱등 작업 카탈로그(3-2) 갱신 — 모든 새 진입점 추가 시
- **ADR 필요**: 클라이언트 제공 키 채택, 시간 제한 윈도우 도입, 메모리 캐시 메커니즘 도입, 영구 윈도우에서 다른 윈도우로 전환
- **거의 발생 안 함**: 4차원 분류 체계(키·메커니즘·응답·윈도우), 키 출처 분류, 외부 보장 + 내부 보장 이중 원칙

`system-value-topology` Tier 1 가치 *멱등성*의 구체 설계. 이 문서는:

- **외부 시스템 멱등 보장과의 책임 분리**를 명시 (9장)
- **멱등성 위반의 안티패턴**을 미리 박제 (13장)
