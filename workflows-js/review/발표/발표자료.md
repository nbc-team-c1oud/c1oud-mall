# c1oud-mall 발표 자료 — PPT 슬라이드 데이터 정리

> PPT 만들 때 그대로 슬라이드 단위로 옮겨갈 수 있게 정리한 데이터 모음.
> 슬라이드별로 **핵심 메시지(슬라이드 본문)** + **발표 노트(말로 풀 내용)** 분리.

## 슬라이드 1 — 프로젝트 개요

### 핵심 메시지
**프로젝트명**: `c1oud-mall`
**한 줄 정의**: PortOne V2 SDK 기반 카드+포인트 복합결제·환불을 지원하는 **DDD 기반 MVP 쇼핑몰**

| 구분 | 내용 |
|---|---|
| 주제 | PG 연동 쇼핑몰 백엔드 + FE 통합 |
| 선정 배경 | 실제 결제 도메인의 정합성·멱등성·외부 시스템 협력 문제를 *실전 규모로* 경험 |
| 기획 의도 | "동작하는 코드"가 아닌 *"정합성을 보장하는 코드"* — 운영 트러블의 80%가 결제·환불 영역에서 발생한다는 통계 인식 |
| 차별점 | 결제 확정 7단계 검증 + INSERT-first 웹훅 멱등성 + DB 커밋 후 외부 호출 보상 패턴 — *교과서 ADR과 실 구현 일치* |

### 발표 노트
- "쇼핑몰을 또 만든다"가 아니라 **결제·환불의 트랜잭션 안전성을 어디까지 끌어올릴 수 있는가**가 목표였음
- 단순 CRUD가 아니라 *외부 PG와의 정합성 보장*이 핵심 학습 가치

## 슬라이드 2 — 프로젝트 내용

### 핵심 메시지
**핵심 기능 7개 (마일스톤 단위)**
1. **M1 인증** — JWT 발급 + 보호 API
2. **M2 상품 조회** — 카탈로그 필터·정렬·페이징
3. **M3 장바구니** — 담기·합산·조회·수량변경·삭제
4. **M4 주문** — 미리보기·생성·재고 선차감·취소
5. **M5 포인트** — 잔액·이력·사용·적립·복구·회수
6. **M6 결제** — PortOne V2 SDK + 7단계 검증 + 보상 + 웹훅 멱등
7. **M7 환불** — 부분/전액 + 복합결제 비율 분리 + PG 부분 취소

### 발표 노트
- 7개 마일스톤이 *순차 의존*. M1→M2→M3→M4→M5→M6→M7 순서대로 검증
- 각 마일스톤은 *user story 기반*으로 작성됨 (`milestones-user-stories.md`)

## 슬라이드 4 — 프로젝트 구조 (아키텍처)

### 핵심 메시지

**DDD + 레이어드 + Bounded Context 분리**

```
nbc.c1oud_mall
├── common
│   ├── exception          # ErrorCode, BusinessException, GlobalExceptionHandler
│   ├── response           # ApiResponse<T> 공통 래퍼
│   ├── security           # JWT, CORS, SecurityConfig
│   └── config             # DummyDataInit, JpaConfig
│
├── user            ┐
├── product         │
├── cart            │ ← 7개 Bounded Context
├── order           │   각 BC = 4계층 (presentation/application/domain/infrastructure)
├── point           │
├── payment         │
└── refund          ┘
```

**레이어 의존성 규칙** (CLAUDE.md):
```
presentation ──▶ application ──▶ domain ◀── infrastructure
```
- domain은 어떤 레이어에도 의존 X
- 의존성 방향은 **항상 domain을 향함**

**전역 룰 (`.claude/rules/`)**:
- `consistency.md` — 정합성 zone 3가지 (TX-bound / Event-converged / External-reconciled)
- `idempotency.md` — 멱등성 등급 (S+ / S / A / B)
- `errorhandling.md` — Exception-first + 번역 지점 2곳
- `tx-topology.md`, `Identifier-System-Topology.md` 등 11개 topology 문서

### 발표 노트
- *전역 룰 (`.claude/rules/`)이 이 프로젝트의 핵심 자산*. 코드보다 룰이 먼저 정해진 후 코드가 따라옴
- 11개 topology 문서로 *결정 기준*을 명시 → AI 협업 시 컨텍스트 주입의 베이스

## 슬라이드 5 — 활용 방안 및 기대효과

### 핵심 메시지

**활용 방안**
- PortOne V2 SDK 연동 사례 — 다른 프로젝트 시작점
- 결제·환불 정합성 보장 패턴 — *복합결제·웹훅·보상 트랜잭션*이 필요한 모든 도메인에 재활용
- `.claude/rules/` + topology 문서 — AI 협업 시 컨벤션 컨텍스트 베이스

**기대효과**
- 결제 정합성 100% 보장 (유실/중복 0건)
- 웹훅 멱등성 100% (S+ 등급)
- 외부 PG 장애 시 자동 보상 트랜잭션
- *코드를 짜는 사람과 AI 모두가 같은 룰 위에서 협업* → 결정 시간 단축

### 발표 노트
- 단순 쇼핑몰이 아니라 *재사용 가능한 결제 도메인 템플릿*으로 자리
- 향후 후속 프로젝트(구독결제, 마일리지 등)에 같은 패턴 그대로 적용 가능

## 슬라이드 10 — 기술적 의사결정 (핵심 로직)

### 핵심 메시지

**6가지 핵심 결정** (모두 AI-ADR로 회고 작성됨)

| # | 결정 | 근거 |
|---|---|---|
| 1 | `portonePaymentId` = **UUID v4 + DB UNIQUE** | enumeration 공격 차단, 외부 키 + 내부 멱등 키 이중 역할 |
| 2 | 결제 확정 처리 순서 = **락 순서**와 일치 (Order→Payment→Point→Cart) | 데드락 cycle 방지 (`consistency.md §5`) |
| 3 | **보상 트랜잭션** = DB 커밋 후 외부 호출 + `REQUIRES_NEW` 별도 컴포넌트 | 메인 TX 롤백 + 보상 TX 커밋 분리 |
| 4 | 결제 확정 **7단계 검증** = PortOne 재조회 먼저 → 멱등 가드 → 소유권 → orderId → 상태 → 금액 | 본문 비신뢰 원칙 우선 |
| 5 | 웹훅 멱등성 = **INSERT-first WebhookEvent** (A/B/C 비교 후 A 채택) | DB UNIQUE로 race 차단, 감사 로그 부수 효과 |
| 6 | 복합결제 환불 분배 = **PG floor + 포인트 잔액 흡수** | 합계 보장 100% + 사용자 무손해 |

**문서 자산**:
- 일반 ADR: `src/main/java/.../payment/docs/adr/` (8개)
- AI-ADR: `workflows/living-docs/Ai-adr/` (11개)

### 발표 노트
- 각 결정마다 *AI가 처음 제시한 답*과 *최종 채택한 답*이 다른 경우가 많았음 → AI-ADR "내가 수정한 부분"에 기록
- 결정의 *근거가 룰에 있음* (consistency, idempotency, errorhandling) → 다음 작업자가 룰만 봐도 결정 재현 가능

## 슬라이드 11 — 개발 프로세스 (사용자 흐름)

### 핵심 메시지

**사용자 관점 종단 흐름 (Happy Path)**

```
① 회원가입 (POST /auth/signup)
        │
        ▼
② 로그인 (POST /auth/login) → JWT 발급
        │
        ▼
③ 상품 둘러보기 (GET /products?category=...&sort=price,asc)
        │
        ▼
④ 장바구니 담기 (POST /carts/items)
        │
        ▼
⑤ 장바구니 조회 (GET /carts) → cartItemId 획득
        │
        ▼
⑥ 주문 미리보기 (GET /orders/preview?cartItemIds=...)
        │
        ▼
⑦ 포인트 잔액 확인 (GET /points/balance)
        │
        ▼
⑧ 주문 생성 (POST /orders {cartItemIds, pointUsedAmount})
   → 응답: portonePaymentId (UUID), pgAmount
   → 백엔드 내부: 재고 선차감 + Payment(PENDING) 채번
        │
        ▼
⑨ PortOne SDK 호출 (PortOne.requestPayment)
   totalAmount = pgAmount (포인트 사용액 제외 금액!)
        │
        ▼
⑩ 결제 확정 (POST /payments/confirm {orderId, portonePaymentId})
   → 백엔드: PortOne 재조회 + 7단계 검증 + 단일 TX
   → 주문 CONFIRMED, 결제 COMPLETED, 장바구니 비움, 포인트 사용·적립
        │
        ▼
⑪ 주문 내역·상세 조회 (GET /orders, GET /orders/{id})
        │
        ▼ (선택)
⑫ 환불 요청 (POST /refunds {items: [...], reason})
   → DB 커밋 (재고·포인트 복구 + Refund 저장)
   → PortOne 부분/전체 취소 호출
   → 200 (성공) 또는 202 (DB는 완료, PG 보강 대기)
```

### 발표 노트
- 핵심: ⑧ *주문 생성 한 번에* portonePaymentId·pgAmount·orderId가 응답에 다 옴 → FE는 추가 호출 없이 SDK 호출 가능
- pgAmount 누락 시 PM001 발생 (백엔드 자동 보상)

## 슬라이드 12 — 트러블슈팅 (1) FE-BE 계약

### 핵심 메시지

### CT003 `cartItemId` vs `productId` 혼동
- **문제**: FE가 productId를 `cartItemIds` 필드에 송신 → BE는 cart_item.id로 조회 → `CART_EMPTY` 응답
- **해결**:
  - 임시 우회: `cartItemIds: []` (전체 장바구니 처리)
  - 근본 해결: `GET /api/v1/carts` 신설 + 응답 DTO에 `cartItemId` 포함
- **좋아진 점**: API 응답 설계 원칙 1개 추가 — *생성 직후 ID 필요할 가능성이 있으면 응답 body에 ID 포함*

### `OrderResponse.paymentId` 0 하드코딩
- **문제**: 주문 상세 조회 시 `paymentId=0`이 응답에 항상 잔존
- **해결**: `OrderFacade`에 `PaymentQueryService` 연동 → 실제 PK 반환
- **좋아진 점**: BC 간 *데이터 흐름*이 명시적 — Order BC가 Payment BC를 조회하는 경로 정착

### 발표 노트
- 두 트러블 모두 FE 가이드 v2 → v3 진화 과정에서 해소
- *FE Claude*가 같은 함정 안 밟도록 문서로 명시 (`fe-integration-guide-v2-addendum.md`)

## 슬라이드 13 — 트러블슈팅 (2) 결제 도메인

### 핵심 메시지

### 결제 확정 처리 순서 vs 락 순서 어긋남
- **문제**: AI가 처음에 `Cart → Point → Order` 순서 제시 (UX 우선)
- **그러나**: 컨벤션의 락 순서는 `Order → Payment → Point → Inventory` → 데드락 cycle 위험
- **해결**: 처리 순서 = 락 순서 일치 원칙으로 재정렬
- **좋아진 점**: AI가 첫 답으로 *UX 직관*을 따라가는 경향 인식 → 동시성 영역은 *컨벤션을 프롬프트에 명시*

### self-injection 함정 (보상 트랜잭션)
- **문제**: AI가 `@Autowired private MyService self;` 패턴 제시 → 가독성 ↓ + 순환 참조 의심
- **해결**: 별도 `@Component(PaymentCompensationTxOp)` + `REQUIRES_NEW`로 분리
- **좋아진 점**: *`XxxTxOp` 컴포넌트 패턴*이 트랜잭션 경계 분리의 표준 — RefundTxOp도 같은 패턴 재사용

### `MockInventoryService` 제거 + productId 정렬
- **문제**: confirm 단계 inventory 호출이 *무엇을 하는지* 모호 (Order 생성 시 이미 차감)
- **해결**: 호출 자체 제거 + 보상 흐름은 `ProductService` 직접 호출 + productId 정렬로 데드락 cycle 차단
- **좋아진 점**: *port 도입 기준*("시그니처 안정 + 어댑터 ≥ 2") 명문화 → 조기 추상화 회피

### 발표 노트
- 상세 회고: `workflows/review/state/2026-06-09-*` 7개 파일
- 트러블 → 해결 → 룰로 정착 → 다음 작업에서 자동 적용

## 슬라이드 14 — 트러블슈팅 (3) 환불·운영

### 핵심 메시지

### 복합결제 환불 분배 — 합계 보장 위반 함정
- **문제**: Round half up은 합계가 어긋남 / Ceil to PG는 외부 거부 위험
- **해결**: PG floor + 포인트 잔액 흡수 → `pointRefund = total - pgRefund` *정의로* 합계 보장
- **좋아진 점**: "합계 보장은 *정의로* 만족시켜라" 사고법 정착

### 환불 race condition — 사전검증만으론 부족
- **문제**: AI 초안은 *상태 기반*(B 등급) → 동시 환불 시 잔여 수량 음수 가능
- **해결**: 사전검증 (fast-fail) + 비관적 락 + 재검증 이중(**S+ 등급**) 도입
- **좋아진 점**: `idempotency.md` 등급표가 *실제 코드 결정의 기준*으로 자리

### 운영 배포 직전 — CORS 하드코딩 + JWT 시크릿 dev 기본값
- **문제**: 
  - `SecurityConfig.java:83-86`에 `http://localhost:*` 하드코딩 → 운영 FE 차단
  - `application-dev.yml`의 JWT_SECRET dev 기본값이 운영 잔존 시 토큰 위조 가능
- **해결**: `production-deployment-checklist.md` 작성 + 환경변수 driven CORS 패턴 제시
- **좋아진 점**: 기능 ADR과 *별개로* 운영 체크리스트 유지 → 다음 Product도 같은 루틴

### 발표 노트
- 운영 진입 직전이 *가장 좋은 보안 점검 타이밍* — 체크리스트 작성 행위 자체가 함정 발견 트리거

## 슬라이드 17 — 잘한 부분 / 아쉬운 부분

### 핵심 메시지

### 잘한 부분
1. **룰·topology·ADR 3중 문서 체계** — 결정 근거가 항상 어딘가에 박혀 있음. AI 컨텍스트 주입에도 활용
2. **AI-ADR "내가 수정한 부분" 명시** — AI 제안을 *비판 없이 통과시킨 사례*가 의심 대상이 되도록 구조화
3. **마일스톤 user test 분리축** — 코드 진척과 *별개*로 사용자 검증축이 살아있음
4. **트러블슈팅 회고를 *팀 컨벤션*으로 정착** — Mock 제거 절차, isCompensable 화이트리스트, port 도입 기준 등이 회고에서 룰로 승격
5. **FE 가이드 v1→v2→v3 진화 추적** — *변경 델타*가 명시적 → FE Claude도 같은 함정 안 밟음
6. **PortOne 보상 트랜잭션 패턴** — DB 커밋 후 외부 호출 + 별도 컴포넌트 + isCompensable 화이트리스트가 *교과서 ADR과 일치하게 구현*

### 아쉬운 부분
1. **FE-BE 계약 typo (`orderstatus`, `createAt`) 잔존** — v3 가이드에 명시되어 있으나 *원인 수정*은 미완
2. **PortOne 취소 자동 재시도 없음** — 1회 실패 시 운영 보강 필요. 자동 재시도 ADR 별도 진행 필요
3. **WebhookEvent 보존 정책 미구현** — 무한 증가, 90일 아카이브 잡 별도 작업
4. **포인트 이력 경로 typo (`/points/histoties`)** — v3 가이드에 명시되어 FE도 같은 철자로 호출 중. 운영 진입 전 수정 필요
5. **운영 진입 직전에 CORS 하드코딩 발견** — 더 일찍 운영 체크리스트 작성했어야
6. **port 추상화 없는 직접 호출이 *다중 인스턴스* 환경에서 어떻게 진화할지 미정**

### 발표 노트
- 잘한 부분 6 = 아쉬운 부분 6 — *균형 잡힌 회고*
- 아쉬운 부분이 *명시적*이라는 게 잘한 점 — 다음 작업의 명확한 시작점
