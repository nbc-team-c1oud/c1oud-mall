## Claude Code 활용 패턴

- [ ] **페어 프로그래밍으로 Claude Code 쓰기** — 혼자 고민하는 것 vs AI에게 먼저 물어보는 것의 속도 차이
- [ ] **도메인 오너십 + Stop & Ask** — AI가 범위 밖 수정 전 물어보는 규칙이 실제로 작동하는지
- [ ] **자동 commit 흐름** — 논리 단위마다 AI가 commit하는 방식이 git log 품질에 미친 영향
- [ ] **CLAUDE.md 컨벤션 파일 효과** — 프로젝트 규칙을 CLAUDE.md에 써뒀을 때 AI 코드 품질 변화
- [ ] **메모리 시스템 활용** — `MEMORY.md`에 팀 결정·피드백을 축적한 뒤 대화 간 일관성이 유지되는가

## 프롬프트 & 지시 전략

- [ ] **지시 단위 크기** — Story 단위로 지시할 때 vs Epic 단위로 지시할 때 결과 품질 차이
- [ ] **"왜"를 포함한 지시** — 배경 없이 "X를 만들어줘" vs 이유·제약·트레이드오프를 같이 주는 것의 차이
- [ ] **토폴로지 문서 선제공** — 작업 전 topology 파일을 주고 시작할 때 오류 수가 줄었나
- [ ] **Stop & Ask 트리거 설계** — AI가 알아서 멈춰야 하는 상황을 CLAUDE.md에 명시할 때 정확도
- [ ] **코드 예시를 규칙 파일에 넣는 효과** — `dto.md`, `exception.md`에 코드 스니펫을 박았을 때 일관성 향상

## 워크플로우 문서 구조

- [ ] **Product / Epic / Story 계층** — 큰 기능을 이 계층으로 쪼갰을 때 진행 추적이 쉬워졌나
- [ ] **Topology 문서 pinning** — 구간 고정 topology를 작업 시작 전 박아두는 방식의 효과
- [ ] **topics.md 카탈로그** — AI에게 학습 토픽 카탈로그를 생성시키는 방법과 활용
- [ ] **living doc vs pinned doc** — 변하는 문서와 고정 문서를 분리했을 때 혼동이 줄었나
- [ ] **ADR을 AI가 쓸 때** — AI가 초안을 쓰고 사람이 검토하는 흐름의 품질과 속도

## 협업 경계 설계

- [ ] **AI 자율성 수준 조정** — 어떤 결정은 AI가 자율적으로, 어떤 결정은 물어보게 설계한 기준
- [ ] **MCP 도구 vs gh CLI 선택** — `mcp__github__*` 대신 `gh` CLI를 고집한 이유와 실제 차이
- [ ] **AI 피드백 루프** — AI가 잘못된 방향으로 가기 시작했을 때 빠르게 잡는 방법
- [ ] **반복 지적 제거** — 같은 피드백을 반복하지 않도록 MEMORY.md나 CLAUDE.md에 저장한 경험

## 학습 도구로서의 AI

- [ ] **설계 토론 상대로 활용** — "이 방식의 트레이드오프가 뭐야?" 같은 질문으로 설계를 탐색한 경험
- [ ] **틀린 코드 의도적 생성 후 수정** — AI가 틀린 코드를 냈을 때 왜 틀렸는지 분석한 경험
