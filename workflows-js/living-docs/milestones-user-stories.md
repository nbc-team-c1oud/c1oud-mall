# c1oud-mall 사용자 관점 마일스톤

> 각 도메인이 완성됐을 때 **사용자(=jun 본인 또는 동료)가 손으로 따라가며 "이게 되는가?"를 직접 확인**하기 위한 acceptance 문서.
> 개발자 작업 계획은 `payment-integration-report-v2.md` / `order-bc-changes-for-payment-integration.md` 참고.
> 본 문서는 **검증축** — 코드가 무엇을 한다는 게 아니라, 사용자 입장에서 무엇이 일어나야 하는가.

---

## 0. 한 줄 요약 + 마일스톤 카탈로그

> 회원가입부터 환불까지 7개 마일스톤을 순서대로 따라가면 c1oud-mall의 전체 기능이 명세대로 동작하는지 확인할 수 있다.

| M | 이름 | 한 줄 검증 | 현재 백엔드 |
|---|---|---|---|
| **M1** | 인증 | 가입 → 로그인 → 토큰으로 내 정보 조회 | ✅ 가능 |
| **M2** | 상품 조회 | 카탈로그를 필터·정렬·페이지로 둘러보고 상세 보기 | ✅ 가능 |
| **M3** | 장바구니 | 상품을 담고 같은 상품 다시 담아 수량 합산되는지, 재고 초과 거부되는지 | ⚠️ 부분 (담기만, 조회/수량/삭제/비우기 없음) |
| **M4** | 주문 | 미리보기 → 결제하기 클릭 시점에 주문+결제 동시 생성, 재고 선차감, 취소 시 재고 복구 | ⚠️ 부분 (미리보기·생성·내역·상세는 OK, **사전등록 호출 없음**, 취소 없음) |
| **M5** | 포인트 | 잔액 보기, 거래내역(사용·적립·사용복구·적립회수) 확인 | ❌ 막힘 (도메인 미구현) |
| **M6** | 결제 | 장바구니→주문→PortOne SDK→confirm → 주문완료·장바구니 초기화. 웹훅 중복도 안전 | ⚠️ 부분 (`/confirm` OK, 사전등록 호출 X, 웹훅은 stub) |
| **M7** | 환불 | 주문 상세에서 환불 상품·수량 선택. 복합결제면 PG·포인트 분리, 재고 부분 복구 | ❌ 막힘 (도메인 미구현) |

## 1. 사용 방법

각 마일스톤은 6칸 표준 구조:

- 🎯 **목표** — 한 줄 요약
- 👤 **User Story** — "회원으로서 ___ 할 수 있어야 한다. 그래야 ___ 할 수 있다." 형식
- 🧪 **검증 시나리오** — 손으로 따라갈 수 있는 step-by-step (Postman/curl/FE 어디서든)
- ✅ **확인 포인트 체크리스트** — `- [ ]`로 직접 체크 가능
- 🔗 **선행 마일스톤** — 어디가 먼저 끝나야 하는가
- 🏗 **현재 상태** — 지금 직접 해볼 수 있는 범위

검증 환경 셋업은 §10, 종단 시나리오는 §11 참고.

## 2. 마일스톤 M1 — 인증

### 🎯 목표
회원이 가입·로그인할 수 있고, 받은 토큰으로 보호된 API에 접근할 수 있다.

### 👤 User Story
- 비회원으로서, 이메일·비밀번호·이름·전화번호를 입력해 회원가입할 수 있어야 한다. 그래야 c1oud-mall을 이용할 수 있다.
- 회원으로서, 이메일·비밀번호로 로그인하고 토큰을 받아야 한다. 그래야 보호된 API(내 정보·주문·결제)에 접근할 수 있다.
- 회원으로서, 다른 사람이 내 토큰 없이 내 정보를 못 보게 막아야 한다. 그래야 안심하고 쓸 수 있다.

### 🧪 검증 시나리오

**시나리오 1 — 정상 가입·로그인 흐름**
1. `POST /api/v1/auth/signup`에 `email=test@example.com`, `password=password123`, `name=홍길동`, `phoneNumber=010-1234-5678` 전송
   - 이렇게 확인: 200 OK, `success=true`, `code=OK` 응답
2. 같은 이메일로 한 번 더 가입 시도
   - 이렇게 확인: 409 Conflict, `code=U001`, `message="이미 사용 중인 이메일입니다."`
3. `POST /api/v1/auth/login`에 위 이메일·비밀번호 전송
   - 이렇게 확인: 200 OK, `data.accessToken`이 길쭉한 JWT 문자열, `data.tokenType="Bearer"`
4. 받은 토큰을 `Authorization: Bearer <token>` 헤더에 넣고 `GET /api/v1/auth/me` 호출
   - 이렇게 확인: 200 OK, `data`에 가입 시 입력한 이메일·이름·전화번호가 그대로

**시나리오 2 — 로그인 실패**
1. 잘못된 비밀번호로 `POST /api/v1/auth/login`
   - 이렇게 확인: 401 Unauthorized, `code=U002`, `message="이메일 또는 비밀번호가 올바르지 않습니다."`
2. 존재하지 않는 이메일로 로그인
   - 이렇게 확인: **같은 메시지**(`U002`). 다른 메시지면 보안 위반

**시나리오 3 — 토큰 검증**
1. 토큰 없이 `GET /api/v1/auth/me` 호출
   - 이렇게 확인: 401, `code=U004`(인증 토큰 없음)
2. 임의 문자열을 토큰으로 보내기
   - 이렇게 확인: 401, `code=U005`(유효하지 않은 토큰)
3. 1시간 이상 지난 토큰(또는 `jwt.expiration`을 잠시 1초로 줄여 발급)으로 호출
   - 이렇게 확인: 401, `code=U006`(만료된 토큰)

### ✅ 확인 포인트
- [ ] 가입 시 비밀번호가 평문이 아니라 암호화되어 DB에 저장 (H2 콘솔에서 `users` 테이블 확인 — bcrypt 해시 형태)
- [ ] 이메일 중복 시 가입 거부 (`U001`)
- [ ] 로그인 응답에 JWT(`accessToken`) + `tokenType="Bearer"`
- [ ] 토큰으로 보호 API 호출 가능
- [ ] 잘못된 비밀번호 vs 존재하지 않는 이메일이 **같은 메시지**로 응답 (보안)
- [ ] 토큰 없음/무효/만료 각각 다른 ErrorCode (`U004`/`U005`/`U006`)

### 🔗 선행
없음 (1번 마일스톤)

### 🏗 현재 상태
**✅ 가능** — 전체 시나리오 수행 가능

## 3. 마일스톤 M2 — 상품 조회

### 🎯 목표
회원/비회원 누구나 상품 카탈로그를 보고 필터링·정렬·페이징할 수 있다.

### 👤 User Story
- 사용자로서, 상품 목록을 카테고리·가격·판매상태로 필터링할 수 있어야 한다. 그래야 원하는 상품을 빠르게 찾을 수 있다.
- 사용자로서, 가격 오름차순·내림차순·최신순으로 정렬할 수 있어야 한다.
- 사용자로서, 한 페이지에 너무 많이 나오지 않도록 페이지 크기를 조정할 수 있어야 한다.
- 사용자로서, 특정 상품의 상세(설명·재고·판매상태)를 볼 수 있어야 한다.

### 🧪 검증 시나리오

**사전 조건**: DB에 더미 상품 3종류 이상 (판매중 정상재고 / 판매중 재고1개 / 품절)

**시나리오 1 — 목록 조회**
1. `GET /api/v1/products?page=0&size=20&sort=createdAt,desc` (토큰 없이도 호출 가능)
   - 이렇게 확인: 200 OK, `data.content`에 상품 배열, `data.totalElements`에 전체 개수
2. `GET /api/v1/products?category=Electronics&minPrice=10000&maxPrice=100000&status=SALE`
   - 이렇게 확인: 필터 조건 모두 만족하는 상품만 응답
3. `GET /api/v1/products?sort=price,asc`
   - 이렇게 확인: `data.content[0].price ≤ content[1].price ≤ ...`

**시나리오 2 — 페이지네이션**
1. 더미 상품을 21개 이상 만든 뒤 `GET /api/v1/products?page=0&size=10`
   - 이렇게 확인: `data.content.length === 10`, `data.totalPages ≥ 3`, `data.first=true`, `data.last=false`
2. `?page=1&size=10`
   - 이렇게 확인: 다른 상품 10개

**시나리오 3 — 상세 조회**
1. 목록에서 ID 하나를 골라 `GET /api/v1/products/{productId}`
   - 이렇게 확인: 200 OK, `description` 필드까지 포함된 상세
2. 없는 ID로 호출
   - 이렇게 확인: 404, `code=PRD001`(존재하지 않는 상품)

### ✅ 확인 포인트
- [ ] 비로그인 상태로도 호출 가능 (인증 불필요)
- [ ] 카테고리·가격·상태 필터 각각 동작, 조합도 동작
- [ ] 정렬 3종(`createdAt,desc` / `price,asc` / `price,desc`) 동작
- [ ] 페이지네이션 `page`, `size`, `totalPages`, `first`, `last` 정확
- [ ] 품절 상품도 목록에 표시되며 `status="SOLD_OUT"`로 식별됨
- [ ] 상세 응답에 `description` 포함, 목록 응답에는 description 없음 (응답 크기 차별화)
- [ ] 없는 상품 ID는 PRD001로 404

### 🔗 선행
없음

### 🏗 현재 상태
**✅ 가능** — 컨트롤러·서비스 구현됨 (FE 가이드 §5 참고)

## 4. 마일스톤 M3 — 장바구니

### 🎯 목표
회원이 본인 장바구니에 상품을 담고, 수량을 조절하고, 빼고, 비울 수 있다.

### 👤 User Story
- 회원으로서, 마음에 드는 상품을 장바구니에 담아둘 수 있어야 한다. 그래야 한 번에 결제할 수 있다.
- 회원으로서, 같은 상품을 두 번 담으면 수량이 합쳐져야 한다. 그래야 중복으로 결제하지 않는다.
- 회원으로서, 재고보다 많이 담으려 하면 거부되어야 한다. 그래야 결제 시점에 실패하지 않는다.
- 회원으로서, 내 장바구니에 뭐가 들었는지 보고, 수량을 바꾸고, 빼거나 다 비울 수 있어야 한다.
- 회원으로서, 남의 장바구니는 절대 보거나 건드릴 수 없어야 한다.

### 🧪 검증 시나리오

**사전 조건**: M1·M2 통과. 로그인된 회원 A의 토큰 보유.

**시나리오 1 — 담기 & 수량 합산**
1. `POST /api/v1/carts/items` `{productId: 1, quantity: 2}` (A 토큰)
   - 이렇게 확인: 201 Created, `Location: /api/v1/carts/` 헤더
2. 같은 상품 다시 `{productId: 1, quantity: 3}`
   - 이렇게 확인: 201, 그리고 장바구니 조회 시 해당 상품 수량이 **5개**(2+3 합산)
3. `{productId: 1, quantity: 0}` 또는 음수
   - 이렇게 확인: 400, `code=C001` 또는 `CT004`(수량은 1 이상)

**시나리오 2 — 재고 초과 거부**
1. 재고 5개인 상품에 `{productId: X, quantity: 10}` 요청
   - 이렇게 확인: 400, `code=PRD002`(재고 부족)
2. 재고 5개인 상품에 3개 담고, 다시 3개 담기 (합산 시 6개 > 재고 5개)
   - 이렇게 확인: 400, `code=PRD002` (합산 후 재고 초과도 거부)

**시나리오 3 — 조회·수량변경·삭제·비우기**
1. `GET /api/v1/carts` (또는 정의된 경로)
   - 이렇게 확인: 내 장바구니 상품 목록 + 각 수량 + 합계 금액
2. 수량 변경 API (예: `PATCH /api/v1/carts/items/{id}` `{quantity: 7}`)
   - 이렇게 확인: 200, 변경된 수량으로 다시 조회
3. 단건 삭제 (예: `DELETE /api/v1/carts/items/{id}`)
   - 이렇게 확인: 200/204, 삭제 후 조회 시 사라짐
4. 전체 비우기 (예: `DELETE /api/v1/carts`)
   - 이렇게 확인: 200/204, 조회 시 빈 배열

**시나리오 4 — 본인 카트만 접근**
1. 회원 B 로그인, B 토큰으로 A의 장바구니 항목 ID로 수량 변경·삭제 시도
   - 이렇게 확인: 403, `code=CRT002`(접근 권한 없음). **A 토큰 없이는 절대 못 건드려야 함**

### ✅ 확인 포인트
- [ ] 인증 없이 호출 시 401
- [ ] 동일 상품 재담기 시 수량 합산
- [ ] 합산 후 재고 초과도 거부
- [ ] 본인 카트만 조회·변경·삭제 가능 (남의 항목 ID로 시도하면 CRT002)
- [ ] 비우기 후 조회 시 빈 배열

### 🔗 선행
M1 (토큰), M2 (담을 상품)

### 🏗 현재 상태
**⚠️ 부분** — 시나리오 1~2 중 "담기"만 가능. 시나리오 3·4의 **조회·수량변경·삭제·비우기 엔드포인트가 부재**. 추가로 `CartController`가 `memberId=1L` 하드코딩이라 시나리오 4의 본인 검증이 의미 없음 (모든 호출이 ID=1 사용자 카트에 들어감). 백엔드 추가 후 본 마일스톤 재검증 필요.

## 5. 마일스톤 M4 — 주문

### 🎯 목표
회원이 장바구니에서 주문서를 미리 보고, "결제하기"를 누른 시점에 주문+결제가 함께 만들어진다. 결제 대기 상태에서 직접 취소하면 재고가 즉시 복구된다.

### 👤 User Story
- 회원으로서, 결제하기 전에 어떤 상품이 얼마에 결제될지 미리보고 싶다. 그래야 안심하고 결제 버튼을 누를 수 있다.
- 회원으로서, 결제하기를 누른 순간 주문번호와 결제 식별자를 받아야 한다. 그래야 PortOne 결제창을 띄울 수 있다.
- 회원으로서, 결제 대기 상태인 주문을 직접 취소할 수 있어야 한다. 그래야 마음이 바뀌면 빠져나올 수 있다.
- 회원으로서, 주문 취소 즉시 차감되었던 재고가 다시 살아나야 한다. 그래야 다른 사람이 살 수 있고 나도 다시 시도할 수 있다.
- 회원으로서, 내 주문 목록과 상세를 볼 수 있어야 하지만 남의 주문은 못 봐야 한다.

### 🧪 검증 시나리오

**사전 조건**: M1~M3 통과. 회원 A 로그인. 장바구니에 상품 2~3개 담겨있음.

**시나리오 1 — 주문서 미리보기 (읽기 전용)**
1. `GET /api/v1/orders/preview` (cartItemIds 없이 = 장바구니 전체)
   - 이렇게 확인: 응답에 각 상품의 **현재가**·수량·소계, 총액 포함
2. 미리보기 호출 전후로 상품 재고 변화 없는지 확인 (H2 콘솔)
   - 이렇게 확인: 재고 그대로. **미리보기는 절대 재고를 건드리지 않는다**
3. 특정 상품만 골라 `?cartItemIds=1,3`
   - 이렇게 확인: 선택된 2개만 응답에 포함

**시나리오 2 — 주문 생성 (재고 선차감 + 결제 사전등록)**
1. 주문 전 상품 X의 재고를 H2에서 메모
2. `POST /api/v1/orders` `{cartItemIds: [1, 2]}`
   - 이렇게 확인: 200, `data`에 `orderId`, **`portonePaymentId`**(UUID 36자), `orderNumber`(`ORD-20260604-XXXXXXXXXXXX` 형태), `orderStatus="PENDING_PAYMENT"`, `totalAmount`
3. H2 콘솔에서 상품 X 재고 확인
   - 이렇게 확인: 주문 수량만큼 **즉시 차감**되어 있음 (결제 완료 아닌데도)

   - 이렇게 확인: 같은 `portonePaymentId`의 결제 레코드가 `status=PENDING`으로 함께 생성됨. `pg_amount`는 (총액 - 포인트 사용액)

   - 이렇게 확인: **장바구니는 그대로 남아 있음** (결제 완료 시점에만 비워지는 규칙)

**시나리오 3 — 재고 부족 시 롤백**
1. 재고 5개인 상품에 수량 10 요청 (장바구니 합산 결과)
   - 이렇게 확인: 400, `code=PRD002`
2. H2에서 상품 재고 확인
   - 이렇게 확인: **변화 없음** (트랜잭션 롤백)
3. `orders`, `payments` 테이블 확인
   - 이렇게 확인: 해당 사용자의 새 주문·결제 레코드 **없음** (롤백)

**시나리오 4 — 주문 취소 (결제대기 한정)**
1. 시나리오 2로 생성한 주문 ID로 취소 API 호출 (예: `POST /api/v1/orders/{id}/cancel`)

3. 같은 주문 다시 취소
   - 이렇게 확인: 200 (멱등) **또는** 409/이미 취소 — 어느 쪽으로 결정했는지 명세화

**시나리오 5 — 조회**
1. `GET /api/v1/orders` (A 토큰)
   - 이렇게 확인: A의 주문만 최신순
2. `GET /api/v1/orders/{orderId}` (남의 주문 ID)
   - 이렇게 확인: 404, `code=OD001` (권한 노출 회피)

## 6. 마일스톤 M5 — 포인트

### 🎯 목표
회원이 자기 포인트 잔액을 보고, 거래내역(사용·적립·사용복구·적립회수)을 확인할 수 있다. 결제·환불 시 포인트가 정확히 변동한다.

### 👤 User Story
- 회원으로서, 내 포인트 잔액을 언제든 볼 수 있어야 한다.
- 회원으로서, 어떤 거래로 포인트가 얼마나 들어왔는지/나갔는지 내역을 보고 싶다.
- 회원으로서, 결제할 때 보유 포인트를 자유롭게 사용할 수 있어야 한다 (잔액 한도 내).
- 회원으로서, 결제가 완료되면 PG 실결제 금액의 1%가 자동 적립되어야 한다.
- 회원으로서, 환불받으면 사용했던 포인트는 다시 돌아오고, 적립받았던 포인트는 회수되어야 한다.

### 🧪 검증 시나리오

**사전 조건**: M1 통과. 회원 A에게 더미 포인트 10,000원 DB 직접 INSERT.

**시나리오 1 — 잔액 조회**
1. `GET /api/v1/points/balance` (A 토큰)
   - 이렇게 확인: `data.balance = 10000`

**시나리오 2 — 거래내역 조회**
1. `GET /api/v1/points/transactions`
   - 이렇게 확인: 최신순, 각 거래에 `type`(`USE`/`EARN`/`USE_RESTORE`/`EARN_REVOKE`), `amount`, `createdAt`
2. 신규 회원이면 빈 배열

**시나리오 3 — 결제 시 포인트 사용 (M6 통합)**
1. M6의 주문 생성에서 `pointUsedAmount=3000`으로 요청
2. 결제 완료 후 `GET /api/v1/points/balance`
   - 이렇게 확인: `balance = 10000 - 3000 + (PG실결제액의 1%)`
3. 거래내역
   - 이렇게 확인: `USE -3000` 한 줄, `EARN +N` 한 줄 (1% 적립)

**시나리오 4 — 환불 시 포인트 복구 (M7 통합)**
1. M7의 환불 후 잔액 조회
   - 이렇게 확인: 사용했던 포인트 복구 + 적립받았던 포인트 비례 회수
2. 거래내역
   - 이렇게 확인: `USE_RESTORE +K`, `EARN_REVOKE -L` 두 줄 추가

**시나리오 5 — 잔액 초과 사용 시도**
1. 잔액 10,000원인데 결제에서 `pointUsedAmount=20000` 요청
   - 이렇게 확인: 400, 잔액 부족 에러 (코드는 명세 후 부여)

### ✅ 확인 포인트
- [ ] 잔액 조회 200 + 정확한 값
- [ ] 거래내역 4종 타입 모두 표시
- [ ] 결제 완료 시 1% 자동 적립 (PG 실결제액 기준, 포인트 사용액 제외)
- [ ] 환불 시 사용 포인트 복구 + 적립 포인트 회수
- [ ] 잔액 초과 사용 거부
- [ ] 모든 거래가 거래내역에 1행씩 기록 (잔액 변동 ≠ 기록 누락)

### 🔗 선행
M1. M3·M4·M6·M7 통합 검증은 해당 마일스톤과 함께

### 🏗 현재 상태
**❌ 막힘** — 포인트 도메인 자체가 미구현. 잔액·거래내역 엔드포인트 없음. 백엔드 추가 필요.

## 7. 마일스톤 M6 — 결제 (PortOne 복합결제 + 웹훅) ⭐

### 🎯 목표
장바구니→주문 생성→PortOne 결제창→`/confirm` 흐름이 끝나면 주문완료·결제완료·장바구니 초기화·포인트 정산까지 한 트랜잭션으로 마무리된다. 검증 실패 시에는 PG 결제가 자동 취소되고 재고가 복구되며 장바구니는 그대로 유지된다. 웹훅이 동시에 또는 중복으로 와도 안전하다.

### 👤 User Story
- 회원으로서, 주문 생성 후 PortOne 결제창에서 카드 결제를 끝내면 그 결과가 c1oud-mall에도 반영되어야 한다.
- 회원으로서, 결제가 정상이면 주문이 완료되고 장바구니가 비워지고 포인트가 적립되어야 한다.
- 회원으로서, 결제 도중 뭔가 잘못되면(금액 변조, PG 실패) 내 카드는 자동 취소되고 재고도 살아나고 장바구니는 그대로여서 다시 시도할 수 있어야 한다.
- 회원으로서, "결제하기" 버튼을 더블클릭해도 중복 결제·중복 적립이 일어나지 않아야 한다.
- 회원으로서, PortOne 서버가 같은 결과를 여러 번 알려와도(웹훅) 시스템이 같은 동작을 반복하지 말아야 한다.

### 🧪 검증 시나리오

**사전 조건**: M1~M4·M5 통과. PortOne 콘솔에 storeId·channelKey·V2 API Secret·웹훅 Secret 발급. 더미 상품·포인트 셋업.

#### 시나리오 1 — 정상 결제 흐름 (행복 경로)
1. 회원 A 로그인 → 카트에 상품 X(가격 30,000원, 재고 5) 1개, Y(20,000원, 재고 10) 1개 담기
2. `POST /api/v1/orders` `{cartItemIds: [...], pointUsedAmount: 5000}` (포인트 5000 사용)
   - 이렇게 확인: `totalAmount=50000`, `pgAmount=45000`, `portonePaymentId=<UUID>`, 상품 재고 4·9로 차감
3. FE에서 `PortOne.requestPayment({ paymentId: <UUID>, totalAmount: 45000, channelKey, storeId, ... })`로 결제창 띄움
4. PortOne 테스트 카드로 결제 완료
5. SDK resolve 후 `POST /api/v1/payments/confirm` `{orderId, portonePaymentId}` 호출
   - 이렇게 확인:
     - 200 OK, `data.status="COMPLETED"`, `alreadyCompleted=false`
     - DB: `orders.order_status=CONFIRMED`, `payments.status=COMPLETED`, `pg_tx_id` 채워짐, `confirmed_at` 채워짐
     - 장바구니: A의 카트 비워짐
     - 포인트: A의 잔액 변동 = -5000(사용) + 450(=45000×1% 적립) → 거래내역 2건 추가
     - 재고: 차감 상태 그대로 유지(추가 차감 없음)

#### 시나리오 2 — 멱등성 (사용자 더블클릭)
1. 시나리오 1의 `/confirm`을 같은 페이로드로 한 번 더 호출
   - 이렇게 확인: 200 OK, `alreadyCompleted=true`
   - DB·포인트·장바구니: **변화 없음** (사이드이펙트 중복 X)

#### 시나리오 3 — 금액 변조 검증 (PM001)
1. 주문 생성 후 PortOne SDK 호출 시 **`totalAmount: 1000`처럼 우리 pgAmount와 다른 값**으로 결제 시도
2. 카드 결제는 1000원으로 PortOne 측에서는 정상 완료
3. `/confirm` 호출
   - 이렇게 확인:
     - 4xx, `code=PM001`(결제 금액 불일치)
     - PortOne: 카드 1000원이 **자동 취소**됨 (PortOne 콘솔에서 cancelled 확인)
     - DB: `payments.status=FAILED`, `orders.order_status=CANCELLED`
     - 재고: 차감되었던 X·Y 재고 **복구**
     - 장바구니: **그대로 유지** (재시도 가능)
     - 포인트: 변동 없음 (사용 안 됐고 적립도 안 됨)

#### 시나리오 4 — PortOne 결제 미완료 (PM007)
1. PortOne 결제창에서 사용자가 결제 직전 취소
2. SDK는 실패로 resolve하지만 실수로 `/confirm`을 호출했다고 가정
   - 이렇게 확인: 4xx, `code=PM007`(PortOne 결제 상태 PAID 아님)
   - 동작: 시나리오 3과 동일 (보상)

#### 시나리오 5 — 본인 결제 아님 (PM006)
1. 회원 A가 만든 주문의 `portonePaymentId`를 회원 B가 알아내서 B 토큰으로 `/confirm` 호출
   - 이렇게 확인: 403, `code=PM006`(소유권 검증 실패)
   - 동작: 보상 트랜잭션 **트리거 안 됨** — A의 결제를 B가 잘못 호출했다고 카드를 취소해버리면 안 됨

#### 시나리오 6 — 주문 ID 불일치 (PM010)
1. A의 결제 portonePaymentId + A의 **다른** 주문 ID로 `/confirm`
   - 이렇게 확인: 400, `code=PM010`(결제와 주문 정보 불일치)

#### 시나리오 7 — 웹훅 단독 도착 (confirm 안 부르고 웹훅만)
1. 시나리오 1의 결제창 완료
2. FE의 `/confirm` 호출 차단 (네트워크 오프라인 시뮬레이션)
3. PortOne이 웹훅 `POST /api/v1/payments/webhooks/portone` 발사
   - 이렇게 확인:
     - 서명 검증 통과 → 200 OK
     - 내부적으로는 PortOne 재조회 → `/confirm`과 **같은 도메인 서비스**가 호출되어 시나리오 1의 모든 사이드이펙트가 일어남
     - DB 상태가 confirm 호출과 동일

#### 시나리오 8 — 웹훅 ↔ confirm 양방향 멱등
1. 시나리오 1의 `/confirm` 호출 직후, 같은 결제에 대한 웹훅 도착
   - 이렇게 확인: 웹훅 200 OK, **사이드이펙트 중복 X** (포인트 이중 적립·장바구니 다시 비우기 등 발생 안 함)
2. 순서 반대: 웹훅 먼저, confirm 나중
   - 이렇게 확인: confirm 응답 `alreadyCompleted=true`

#### 시나리오 9 — 웹훅 서명 위변조 (401)
1. `webhook-signature` 헤더를 임의 값으로 위조해서 `POST /webhooks/portone`
   - 이렇게 확인: 401 Unauthorized, 핸들러 호출 안 됨 (서명 필터에서 차단)

### ✅ 확인 포인트
- [ ] 정상 흐름: 주문완료·결제완료·장바구니 초기화·포인트 정산이 **한 번에** 일어남
- [ ] 같은 confirm을 두 번 불러도 사이드이펙트 1회만 (`alreadyCompleted` 응답)
- [ ] **3대 검증 조건** 모두 작동: 상태(PM007)·금액(PM001)·멱등(PM008로 미존재 거부)
- [ ] 보상 트리거: PM001/PM007 → PG 자동 취소 + 재고 복구 + 주문 취소
- [ ] PM006(권한)은 보상 트리거 안 함
- [ ] 장바구니는 **검증 실패 시 유지**, 성공 시에만 비워짐
- [ ] 웹훅 단독으로도 confirm과 같은 결과
- [ ] 웹훅·confirm 양방향 멱등 (어느 쪽이 먼저 와도 사이드이펙트 1회)
- [ ] 웹훅 서명 위조 시 401 + 핸들러 미호출
- [ ] KG이니시스 5만원 자동취소 정책 인지 (테스트 결제는 가급적 5만원 미만 또는 자동취소 감수)

### 🔗 선행
M1·M2·M3·M4·M5 모두

- ❌ **결제 사전등록 호출 부재** (OrderFacade.createOrder → PaymentInitiationService 호출 추가 필요)
- ❌ **웹훅 본문 처리 부재** (Story 3-2 — 현재는 200 OK만)
- ❌ **포인트·장바구니 초기화·주문 완료 모두 mock** — 실 BC 빈 교체 전까지 사이드이펙트는 로그만 (`[MOCK] ...` 형태)

→ 시나리오 1·2의 일부(`/confirm` 응답·상태 전이)는 검증 가능. 사이드이펙트 검증은 Mock 교체 후. 시나리오 3·4·5·6은 검증 가능. 시나리오 7·8(웹훅)은 Story 3-2 후.

## 8. 마일스톤 M7 — 환불

### 🎯 목표
결제 완료된 주문의 일부 또는 전체를 환불할 수 있다. 복합결제(포인트+PG)면 비율대로 분리 환불되고, 재고는 환불된 수량만큼만 복구된다.

### 👤 User Story
- 회원으로서, 산 상품 중 일부만 골라서 환불할 수 있어야 한다.
- 회원으로서, 전체를 환불받으면 주문 자체가 취소되어야 한다.
- 회원으로서, 환불 받을 금액은 **내가 결제했던 시점의 가격**대로 계산되어야 한다 (현재가 X).
- 회원으로서, 환불 받으면 사용했던 포인트는 돌아오고, 적립받았던 포인트는 비례 회수되어야 한다.
- 회원으로서, 같은 상품을 이미 환불한 만큼 또 환불 요청하려 하면 거부되어야 한다.

### 🧪 검증 시나리오

**사전 조건**: M6 시나리오 1 통과. 회원 A가 상품 X 1개(30000원) + Y 1개(20000원) 결제완료, 포인트 5000 사용. PG 실결제 45000원. 적립 450 포인트.

#### 시나리오 1 — 부분 환불 (1품목만)
1. `POST /api/v1/refunds` `{orderId, items: [{orderItemId: X, quantity: 1}], reason: "단순변심"}` (A 토큰)
   - 이렇게 확인:
     - 200 OK, 응답에 산정된 환불 금액 = 30000원 (가격 스냅샷 × 수량)
     - **PG 환불액 + 포인트 환불액**으로 분리 (45000:5000 = 9:1 비율 → PG 27000, 포인트 3000)
     - DB: `refunds` 테이블에 한 행, `pg_refund_amount=27000`, `point_refund_amount=3000`
     - 주문: `order_status` 그대로 `CONFIRMED` (전체 환불 아니므로), `payments.status` = "부분환불"
     - 상품 X 재고: +1 복구. Y는 변화 없음
     - 포인트 잔액: 3000 복구 + 적립 비례 회수(예: 270 회수 — 비율 산식은 구현에 따라)
     - PortOne 콘솔: 해당 결제에 27000원 부분 취소 기록

#### 시나리오 2 — 전액 환불
1. 시나리오 1 후 남은 Y에 대해 `POST /api/v1/refunds` `{orderId, items: [{orderItemId: Y, quantity: 1}], reason: "..."}`
   - 이렇게 확인:
     - 환불 금액 20000원, 분리 (PG 18000, 포인트 2000)
     - 주문: `order_status = CANCELLED` (모든 상품 환불됨), `payments.status` = "환불완료"
     - Y 재고 +1 복구
     - PortOne: 잔액 18000 추가 취소 (총 45000 모두 취소)
     - 포인트: 적립분도 모두 회수, 사용분도 모두 복구

#### 시나리오 3 — 잔여 환불 수량 초과 거부
1. X를 1개 산 주문에 `items: [{orderItemId: X, quantity: 2}]` 요청
   - 이렇게 확인: 400, "잔여 환불 가능 수량 초과" 에러
2. 시나리오 1 후 같은 X를 또 환불 요청 (잔여 0)
   - 이렇게 확인: 동일 거부

#### 시나리오 4 — 본인 주문이 아닌 환불
1. B 토큰으로 A의 주문 환불 요청
   - 이렇게 확인: 403 또는 404(소유권 노출 안 함)

#### 시나리오 5 — 결제 완료 안 된 주문 환불 시도
1. PENDING_PAYMENT 또는 CANCELLED 주문에 환불 요청
   - 이렇게 확인: 거부 (취소 전용 흐름으로 안내)

#### 시나리오 6 — PG 취소 호출 실패 시 (장애 시뮬레이션)
1. PortOne 측 일시 장애로 PG 취소 API가 실패
2. 환불 요청
   - 이렇게 확인:
     - DB는 정상 커밋 (재고·포인트·환불기록 모두 반영)
     - PortOne 측 결제 상태는 PAID 그대로 → 운영자가 reconcile하거나 수동 보정
     - 응답은 클라이언트엔 환불 처리됨 (DB 기준), 서버 로그에 PG 실패 경고 (PM009)

### ✅ 확인 포인트
- [ ] 환불 단위가 **주문 상품 + 수량** (클라이언트가 금액 직접 X)
- [ ] 환불 금액 = 결제 시점 `priceSnapshot × quantity` (현재가 아님)
- [ ] 복합결제 시 결제 비율대로 PG·포인트 분리
- [ ] 부분 환불 시 주문 상태 `CONFIRMED` 유지, 결제 상태 "부분환불"
- [ ] 전액 환불 시 주문 상태 `CANCELLED`로 전이
- [ ] 재고는 환불 수량만큼만 복구
- [ ] 잔여 환불 수량 초과 거부
- [ ] 본인 주문만 환불 가능
- [ ] DB 먼저 커밋 → PG 호출은 트랜잭션 밖
- [ ] PG 호출 실패는 로그 + 운영자 알림 (서비스 응답은 정상)

### 🔗 선행
M6 (결제 완료 주문이 있어야 함), M5 (포인트 복구 검증)

### 🏗 현재 상태
**❌ 막힘** — 환불 도메인 자체가 미구현. `RefundController`·`RefundService`·`Refund` 도메인 모두 없음. 환불 기록 테이블 없음. 백엔드 추가 후 본 마일스톤 작성 가능.

## 11. 전체 종단(end-to-end) 시나리오 — 회원가입부터 환불까지

각 마일스톤 통과 후, 모든 도메인이 완성되면 본 종단 시나리오로 한 번에 회귀 검증.

### 종단 1 — 정상 happy path
1. 회원 A 가입 (M1)
2. A 로그인, 토큰 저장
3. 상품 목록에서 카테고리 Electronics 필터 (M2)
4. 상품 1(커피머신) 장바구니에 1개, 상품 2(머그컵) 2개 담기 (M3)
5. 더미 포인트 10000 셋업 후 잔액 조회 (M5 셋업)
6. 주문서 미리보기 (M4) → 총액 70000 확인
7. 결제하기 클릭 → 주문 생성 + `portonePaymentId` 수령 (M4) → 재고 차감 확인
8. PortOne SDK로 70000원(또는 -포인트 사용액) 결제 (M6)
9. `/confirm` 호출 → 주문완료, 장바구니 비움, 포인트 사용/적립 (M6)
10. 내 주문 상세 조회 → CONFIRMED 확인 (M4)
11. 포인트 잔액·거래내역 변화 확인 (M5)
12. 환불 요청: 머그컵 1개만 환불 (M7)
13. 부분 환불 결과 확인 — PG 부분 취소, 포인트 부분 복구·회수, 재고 +1 (M7·M5)

### 종단 2 — 결제 검증 실패 보상
1. 종단 1과 동일하게 주문 생성까지 진행
2. PortOne SDK에서 `totalAmount`를 1원으로 변조하여 결제
3. `/confirm` 호출 → PM001 응답
4. 확인: PG 카드 자동 취소, 주문/결제 취소 상태, 재고 복구, 장바구니 그대로
5. **같은 장바구니로 다시 주문·결제 시도** → 이번엔 정상 → 성공

### 종단 3 — 더블클릭 / 웹훅 중복
1. 종단 1의 `/confirm`을 1초 안에 5번 연속 호출 (동시성)
2. 확인: 응답 중 1개는 `alreadyCompleted=false`, 나머지는 `alreadyCompleted=true`. 포인트·장바구니·주문완료 사이드이펙트는 1회만
3. PortOne 콘솔에서 웹훅을 수동으로 재전송 (또는 자동 도착)
4. 확인: 200 OK, 사이드이펙트 추가 발생 X
