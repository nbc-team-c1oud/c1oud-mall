`결제`가 단방향 흐름(*주문 → PG → DB*)이라면 `환불`은 4개 컨텍스트(`Refund` 기록·`Payment` 상태·`Point` 잔액·`Inventory` 수량)를 가로질러 *역방향으로 보상 정합성을 회복*하는 작업이며, 단일 결제에 대해 시간을 가로지르는 *누적 잔여 수량 추적*이 추가된다는 점에서 다른 Product와 비대칭이다. 직전 메타 원칙 일관 적용: **Product 단위 = 면접 서사 + 횡단 관심사**. Epic 두 개(*환불 금액 산정* / *환불 처리 트랜잭션*)는 본 카탈로그의 깊이 단면이지만, 본 출력은 *Epic 나열 대신 Product 전체를 가로지르는 결정*에 집중한다.

## 1. *본 Product의 정체성* — 환불의 3축 (정합성 / 보상 / 멱등)

이 Product를 한 줄로 묶는 *정체성 토픽*. 다른 Product와의 비대칭은 이 3축에서 발생한다.

- ***A축. 정합성***: 4개 컨텍스트(`Refund`·`Payment`·`Point`·`Inventory`)를 **단일 TX-bound zone**에서 일관 갱신, *외부 PG 호출은 트랜잭션 밖으로 격리*.
- ***B축. 보상***: DB 커밋 후 PG 취소 호출이 실패하면 *예외가 아닌 운영 이슈*. 호출자로 예외를 되돌리지 않고 `REFUND_PG_CANCEL_FAILED` 로그 마커 + 메트릭으로 처리.
- ***C축. 멱등***: 멱등 키 = **비즈 식별자** `(paymentId, items 집합)`. *서버 채번 키도 클라이언트 헤더도 아닌* 비즈니스 데이터가 키. 동시 진입은 `SELECT ... FOR UPDATE on payments`로 차단.
- **3축의 절충점**: A축 강화는 락 hold time을 늘리고, B축 강화는 사용자 응답 의미를 흐리며, C축 강화는 응답 코드를 `200`/`202`/`409`로 분리하게 만든다. 본 Product는 세 축 모두 *명시적 분리*를 채택.
- **결제 Product와의 비대칭**: 결제는 *외부 호출 → DB 반영* 순서, 환불은 *DB 커밋 → 외부 호출* 순서. **같은 PG 포트를 공유하지만 트랜잭션 위상이 거울 대칭**.
- **면접 가치**: "환불은 결제의 역연산이 아니다. 외부 호출 순서와 보상 책임이 결제와 거울 대칭이며, 멱등 키 출처도 다르다."

## 2. *결제와의 호출 순서 비대칭* — DB-PG 순서 반전의 본질

같은 PG(`PortOnePaymentCancelPort`)를 공유하지만 *외부 호출 시점*이 결제와 환불에서 거꾸로다. 그 이유와 결과가 본 Product 깊이의 출발점.

- **결제 흐름**: PortOne 결제 사전 조회(검증) → DB 트랜잭션(주문완료·결제완료·포인트·재고·장바구니 초기화) → 검증 실패 시 PG 취소 보상.
- **환불 흐름**: 선검증 → **DB 트랜잭션 커밋** → **PG 취소 호출** → 실패 시 보상 로그.
- **순서가 거꾸로인 이유**: 결제는 *외부 결제가 사실의 출처*이므로 외부 상태를 먼저 확인해야 DB 결정이 의미를 갖는다. 환불은 *우리가 결정의 출처*이므로 DB가 먼저 확정되어야 PG 측 취소가 일관된다.
- **공통 원칙**: 어느 쪽이든 **외부 호출은 트랜잭션 밖**. 결제는 호출 후 트랜잭션 진입, 환불은 트랜잭션 커밋 후 호출.
- **트레이드오프**: 결제는 PG 측 멱등성(`paymentId`)에 더 강하게 의존, 환불은 우리 측 DB 멱등성(잔여 수량 누적)에 더 강하게 의존.
- **함정**: 환불에서 PG 먼저 호출 → DB 실패 시 *우리는 DB에 흔적이 없지만 PG는 취소된 상태*. 사용자 화면과 PG 상태가 영구 불일치.
- **면접 가치**: "결제와 환불은 같은 PG 포트를 쓰지만 외부 호출과 트랜잭션의 위상이 거꾸로다. 진실의 출처가 어디인지가 호출 순서를 결정한다."

## 3. *단일 TX-bound zone과 4개 컨텍스트* — `consistency.md §2`의 적용

`consistency.md` zone 모델에서 환불은 *결제 확정과 같은 등급의 TX-bound zone*이다. 어떤 컨텍스트가 같은 트랜잭션에 묶이는지가 본 Product의 정합성 단위.

- **묶이는 4컨텍스트**: `Refund`(기록 저장) / `Payment`(상태 전이, 락 대상) / `Point`(복구 + 적립 회수) / `Inventory`(수량 복구).
- **묶이지 않는 컨텍스트**: 등급·누적 결제금액(`Event-converged`), 알림·메일(`본질적 비멱등`, 별도 흐름), 외부 PG(`External-reconciled`).
- **묶이는 기준** (`consistency.md §3` 셋 이상 만족): 항상 같은 트랜잭션에서 변경 / 불변식 공유 / 한쪽 변경이 다른 쪽 없이 무의미 / 같은 사용자 액션의 일부.
- **불변식**: `재고 복구 수량 + 포인트 복구 금액 + PG 취소 금액 = 산정값`. 어느 하나라도 빠지면 정합성 깨짐 → 단일 트랜잭션 강제.
- **금지 어휘**: "결과적으로 같아진다", "거의 일관" — 본 Product에 적용 금지. *환불 정합성 100%*가 KPI.
- **함정**: 등급 갱신이나 알림까지 같은 트랜잭션에 넣으면 트랜잭션이 5개 이상 컨텍스트를 만지게 됨 → `consistency.md §8` PR 게이트 위반.
- **면접 가치**: "환불 zone은 4개 컨텍스트를 묶고 등급·알림은 잘라낸다. zone 식별은 *불변식 단위*가 기준이다."

## 4. *비관적 락 순서* — `Order → Payment → Point → Inventory`의 데드락 회피

여러 컨텍스트가 락을 잡을 때 순서를 통일하지 않으면 *교차 데드락*이 발생한다. 본 Product는 `consistency.md §5` 락 순서를 그대로 따른다.

- ***고정 순서***: `Order → Payment → Point → Inventory`. 위반 코드는 PR 차단.
- **환불에서의 적용**: Payment에 `SELECT ... FOR UPDATE` → Point 복구 → Inventory 복구. Order는 환불에서 직접 락 X (조회만).
- **락 hold time 최소화**: 락 안에서 **외부 호출 금지**. 락을 잡은 채 PortOne을 호출하면 PG 응답까지 다른 환불 요청이 전부 대기.
- **락 타임아웃**: 무한 대기 금지. 트랜잭션 타임아웃 설정 + 모니터링.
- **단일 인스턴스 가정**: 분산 락 미사용. 다중 인스턴스 도입 시 ADR.
- **함정**: 잔여 수량 검증을 위해 RefundItem 테이블만 락 → Payment 측에서 동시에 상태 전이가 발생하면 race. **Payment를 락 대상 핵심**으로 두는 게 정답.
- **면접 가치**: "락 순서를 어디 적느냐가 아니라 *코드가 그 순서를 강제하느냐*가 본질이다. 환불에서는 Payment가 락 헤드다."

## 5. *외부 호출의 트랜잭션 분리* — DB 락이 PG 응답을 기다리지 않는다

가장 흔한 안티패턴은 *트랜잭션 안에서 외부 호출*. 본 Product가 가장 강하게 거부하는 결정이며, 그 비용 구조가 깊이 단면.

- **금지**: `@Transactional` 메서드 안에서 `restClient.post(...)` 호출.
- **이유**: PortOne 응답이 평소 300ms, 타임아웃 5~10s. 락을 잡은 채 5초 대기하면 *같은 paymentId의 다른 환불 요청·결제 조회·포인트 잔액 조회까지 동시에 블록*.
- **분리 패턴**: 트랜잭션 A에서 DB 커밋(`status=DB_COMMITTED`) → 트랜잭션 밖에서 PG 호출 → 트랜잭션 B(단일 UPDATE)로 `status=PG_CANCELLED`.
- **결과 상태 3분**: `DB_COMMITTED`(PG 대기 또는 실패) / `PG_CANCELLED`(완료) / `FAILED`(드물게 명시 실패).
- **트랜잭션 B의 짧음**: 단일 `UPDATE refunds SET status=?, pg_cancel_tx_id=? WHERE id=?` 한 줄. 다른 컨텍스트 건드리지 않음.
- **트레이드오프**: 트랜잭션을 분리하면 *PG 성공 후 트랜잭션 B 실패* 가능성. 이 경우도 `pgCancelTxId`를 가진 별도 보강 작업으로 수렴.
- **함정**: 트랜잭션 B를 짧게 안 만들고 *PG 호출 후 후처리(알림·로그 정리)까지 같이* 넣으면 분리 효과 소멸.
- **면접 가치**: "외부 호출을 트랜잭션 밖으로 빼는 이유는 *부분 실패 복잡도 분산*이지 단순 성능이 아니다."

## 6. *보상 트랜잭션의 응답 의미* — `200` vs `202`의 비대칭

PG 취소 호출이 실패해도 *DB는 이미 커밋*된 상황. 사용자에게 어떻게 응답할지가 본 Product의 *운영 가시성* 결정 포인트.

- **거부한 옵션**: `200 OK` + `warning` 필드. 사용자에게 *완료처럼* 보임.
- **채택**: `202 Accepted` + `refundStatus=DB_COMMITTED` + `warning` 필드. *수락되었으나 처리 진행 중* 의미.
- **errorhandling.md §6 일관**: "커밋 후 외부 호출 실패는 예외 아닌 보상 처리". 호출자에게 예외를 되돌리지 않는다.
- **운영 흐름**: 로그 마커 `REFUND_PG_CANCEL_FAILED` → 알람 → 수동/스케줄 재시도. 자동 재시도는 1차 제외.
- **사용자 환불 체감**: DB는 이미 복구됨(재고·포인트). PG 측 잔액 복구만 지연. *사용자 손해 없음*이 본 응답 코드의 정당성.
- **함정**: 202로 응답하면 클라이언트가 *재시도*하지 않도록 명세에 명시 필요. 멱등 처리(409로 차단)와 결합.
- **면접 가치**: "PG 실패를 200으로 가리거나 500으로 띄우는 대신 202를 선택한 이유는 *우리 상태의 진실 = 부분 완료* 이기 때문이다."

## 7. *복합결제 비율 분리 산정* — `floor + 잔액 흡수`의 정당성

포인트+PG 복합결제에서 *부분 환불 금액을 결제 수단별로 어떻게 나눌지*. 1원 단위 정확성이 KPI(*비율 분리 산정 오차 0원*).

- **공식**: `pgRatio = pgAmount / totalAmount`, `pgRefundAmount = floor(totalRefund × pgRatio)`, `pointRefundAmount = totalRefund - pgRefundAmount`.
- **소수점 처리**: PG는 `floor`, 포인트는 *잔액*. 1원 단위 끝수를 포인트가 흡수.
- **정당성**: 포인트는 *내부 자원*, PG는 *외부 자원*. PG에 끝수를 몰면 외부 정합성이 깨지고, 포인트에 몰면 사용자 손해 없음(오히려 1원 더 복구).
- **합계 보장**: `pgRefundAmount + pointRefundAmount == totalRefund`가 *항상* 성립. 프로퍼티 기반 테스트로 검증.
- **거부한 옵션**: 등급별 가중 / `round` / `ceil` / 무작위 끝수 분산. 1차 정책은 단순 `floor + 잔액 흡수`.
- **엣지 케이스**: PG-only 결제 → `pgRefundAmount=전액`, `pointRefundAmount=0`. 포인트-only 결제 → 반대.
- **면접 가치**: "비율 분리에서 소수점을 어디로 흘릴지가 본질이다. 외부 자원은 안전한 쪽으로, 내부 자원이 끝수를 흡수한다."

## 8. *가격 스냅샷의 시간 차원* — 1차 OrderItem 조회 vs 정식 PaymentItem

환불 금액은 *결제 시점*의 단가 기준. 결제와 환불 사이에 단가가 변하면 무엇이 진실인가.

- **1차 결정**: RefundItem이 *환불 생성 시점*에 `OrderItem.unitPrice`를 복사 보관. Payment·Order 모델 변경 없음.
- **취약점**: 결제와 환불 사이에 OrderItem 단가가 변경되면 *환불 시점 단가*로 산정. 결제 시점 단가가 아님.
- **정식**: Payment 생성 시 `PaymentItem` 신설 → `priceSnapshotAtPayment` 영구 보관. *시간 차원의 정합성* 확보.
- **거부한 옵션**: 환불 시점에 Order BC API로 *과거 단가 조회*. Order 도메인 책임 증가, 조회 경로 복잡화.
- **후속 마이그레이션**: 정식 스냅샷 도입은 별도 Story. 1차 출시 후 사용자 동의 시 진행.
- **트레이드오프**: 1차 결정은 *Order·Payment 모델 변경 없음 vs 단가 변경 취약*. 단가 변경 빈도가 낮으면 충분.
- **면접 가치**: "환불 금액은 단가 × 수량인데 *어느 시점의 단가*인지가 본질이다. 우리 1차는 환불 생성 시점, 정식은 결제 시점 스냅샷."

## 9. *잔여 환불 가능 수량의 누적 추적* — `SUM` 쿼리 + race 차단

부분 환불이 여러 번 누적되어도 잔여 수량을 정확히 추적해야 한다. *시간을 가로지르는 잔액 추적*이 본 Product의 깊이.

- **계산**: `잔여 = 원래 주문 수량 - SUM(같은 paymentId·orderItemId의 모든 RefundItem.quantity)`.
- **구현 위치**: `RefundRepository.sumRefundedQuantity(paymentId, orderItemId)` — Repository SUM 쿼리. 자바 메모리 합산 대신 DB 집계.
- **선검증**: 트랜잭션 밖 또는 read-only 트랜잭션에서 빠른 거부.
- **트랜잭션 안 재검증**: Payment 락 획득 후 잔여 수량 재계산. 선검증과 재검증 사이 race를 차단.
- **거부한 옵션**: 도메인 서비스가 모든 Refund 로드 후 자바에서 합산. *데이터 양이 늘수록 비용 증가*.
- **테스트 시나리오**: 누적 환불 정확성 / 동시 진입 race / 0 수량 요청 / 음수 입력 / 원 수량과 정확히 같은 누적.
- **면접 가치**: "잔여 수량은 *상태가 아니라 누적값*이다. 매번 계산하고, 트랜잭션 안에서 잠그고, 다시 계산한다."

## 10. *멱등 키 출처의 분류* — 서버 채번 / 비즈 식별자 / 외부 키 / 클라 키

`idempotency.md §3` 분류에서 환불의 멱등 키는 *비즈 식별자*. 어떤 출처가 어떤 상황에서 적합한지가 깊이 단면.

- **서버 채번** (`portonePaymentId`·주문 ID): 우리가 발급, *검증 불필요*. 결제 확정·주문 생성에서 사용.
- **비즈 식별자** (`paymentId + items 집합`): 의미 있는 ID 조합. *소유권 검증 필요*. **환불·회원가입·장바구니에서 사용**.
- **외부 제공** (Webhook의 `paymentId`): 외부 발급, *HMAC 서명 검증* 필수.
- **클라 제공** (`Idempotency-Key` 헤더): *본 프로젝트 채택 안 함*. 위변조·충돌 위험.
- **환불이 비즈 식별자인 이유**: 동일 사용자가 동일 paymentId에 동일 items 조합으로 두 번 요청하면 *의도가 같다*고 판단. 별도 키 발급 부자연.
- **잠금 효과**: 누적 잔여 수량으로 *시간 차원* 멱등이 자연 형성. 두 번째 요청은 잔여 부족으로 차단.
- **면접 가치**: "환불 멱등 키는 서버 채번이 아닌 비즈 식별자. *클라이언트가 우연히 두 번 누른 경우*와 *의도된 추가 환불*을 어떻게 구분하는가가 설계 포인트다."

## 11. *Race 가드의 표준 패턴* — 사전조회 + 트랜잭션 안 재검증 + FOR UPDATE

`idempotency.md §4`의 *S+ 등급* 패턴을 환불에 적용. 단순 유니크 제약으로는 누적 잔여 수량을 막을 수 없다.

- **3단 구조**: (1) 트랜잭션 밖 사전조회로 빠른 거부 → (2) 트랜잭션 안 락 획득(`SELECT ... FOR UPDATE on payments`) → (3) 잔여 수량 재계산·재검증.
- **유니크 제약 한계**: 환불은 *별 환불 여러 건*이 정상 시나리오. `(paymentId, orderItemId)` 단순 유니크는 부분 환불을 막아버림.
- **락 대상**: Payment 행. RefundItem 테이블이 아니라. 같은 paymentId의 환불 요청이 직렬화됨.
- **사전조회의 의미**: 트랜잭션 진입 전에 *명백한 거부*만 빠르게. 동시성은 사전조회로 보장 X.
- **트랜잭션 안 재계산**: 사전조회 통과 후 락을 잡고 *다시 합산*. 그 사이에 다른 환불이 커밋됐다면 여기서 RF001로 거부.
- **테스트**: 두 스레드가 동일 paymentId에 동시 요청 → 한 건만 성공·다른 건 RF001(409). 통합 테스트 필수 DoD.
- **함정**: 락 없이 트랜잭션 안 재계산만 → 같은 트랜잭션 격리 레벨에서도 *행 락이 없으면* race 가능.
- **면접 가치**: "사전조회는 *비용 절감*이지 race 차단이 아니다. 차단은 트랜잭션 안 락 + 재계산 둘 다 필요하다."

## 12. *외부 멱등성에 의존하지 않는다* — PortOne `requestKey`는 비용 절감일 뿐

`idempotency.md §7` 원칙: 외부 보장은 우리 책임의 대체가 아니다. 본 Product의 멱등 책임 분배가 깊이 단면.

- **PortOne 보장**: `paymentId` + `requestKey` 기반 *PG 측 중복 취소 0건*.
- **우리 책임**: 내부 상태 일관성, 부수 처리(포인트·재고), 트랜잭션 경계, 사용자 응답.
- **분리 원칙**: 외부 보장은 *PG 호출이 실수로 두 번 가도 PG 측 정합성을 깨지 않는다*는 정도. 우리 측 환불 기록 단일성은 우리가 보장.
- **`requestKey` 출처**: `"refund-{refund.id}"`. *Refund DB ID*를 그대로 사용. 발급 시점이 분명, 충돌 불가.
- **함정**: PortOne 멱등성을 믿고 우리 측 멱등 가드를 생략 → *PG 호출 후 DB 커밋 전 실패*가 *키 없음 → 재처리*로 흘러 PG는 중복 안 되지만 *우리 DB에는 흔적 없음 → 사용자 화면과 PG 상태 불일치*.
- **응답 못 받음 vs 실패 응답**: 응답 못 받음은 *상태 모름* → 재조회로 해소. 실패 응답은 *실패 확정* → 보상 흐름 진입.
- **면접 가치**: "외부 멱등성은 *외부 정합성*만 보장한다. 내부 정합성은 우리가 잡는다. 분리하지 않으면 부분 실패가 영구화된다."

## 13. *응답 코드의 의미론* — `200` / `202` / `409` / `403`의 분리

본 Product의 응답 코드는 *상태 머신*. 같은 4xx라도 의미가 다르며, 이는 `idempotency.md §5` + `errorhandling.md`의 통합 결과.

- ***200 OK***: PG 취소까지 완료 (`refundStatus=PG_CANCELLED`). *완전한 보상 성공*.
- ***202 Accepted***: DB 커밋 + PG 실패. 수락은 됐지만 *PG 처리 진행 중*. 사용자 손해 없음, 운영팀 후속 확인.
- ***409 Conflict (RF001)***: 잔여 수량 초과. *멱등 충돌*. 사용자가 인지하고 의도 수정 필요.
- ***409 Conflict (RF002)***: 환불 불가 상태 (결제가 COMPLETED 아님). *자원 상태 충돌*.
- ***403 Forbidden (RF003)***: 본인 소유 아님. *소유권 위반*.
- ***401***: Spring Security 자동.
- **400을 안 쓰는 이유**: 잔여 수량 초과는 *입력이 잘못된 게 아니라 상태가 충돌*. `idempotency.md §5` "Explicit reject = 409".
- **면접 가치**: "환불의 4xx는 *입력 문제 vs 상태 충돌*을 분리한다. 400은 입력만, 409는 상태 충돌만."

## 14. *적립 포인트 회수 정책* — 결제 정책 객체의 *공유*가 정답

환불 시 결제 시점에 적립된 포인트도 비례 회수해야 한다. *적립률*의 위치 결정이 본 섹션의 깊이.

- **공식**: `회수 적립 = pgRefundAmount × 적립률`.
- **거부한 옵션**: 환불 서비스에 `0.01` 하드코딩. 결제 적립률이 변경되면 *환불만 따로 어긋남*.
- **채택**: 결제 product의 적립 정책 클래스/상수를 *그대로 참조*. 단일 출처(SSOT).
- **위치 확인**: 1차 진입 시 결제 흐름의 적립률 코드 위치를 식별 후 환불 application에서 import 또는 공통으로 추출.
- **음수 잔액 가드**: 회수 적립 > 현재 잔액 → 잔액을 0으로 만들고 *부족분은 음수 허용 X / 운영 알람*.
- **트레이드오프**: 정책 객체 공유는 *변경 시 영향 범위*가 양 컨텍스트로 전파. 변경 빈도가 낮으면 SSOT 이득이 큼.
- **면접 가치**: "환불의 적립 회수는 결제의 적립률과 *항상 같은 값*이어야 한다. 정책은 객체로 공유하고 숫자를 두 번 적지 않는다."

## 15. *Refund 별도 컨텍스트 결정* — Aggregate 분리 vs 패키지 분리 vs 의존 방향

`Refund`를 어디에 둘지는 단순 패키지 결정이 아니라 *도메인 책임 분할*. 본 Product의 구조적 결정.

- **결정**: 별도 컨텍스트 `nbc.c1oud_mall.refund.{presentation,application,domain,infrastructure}`. payment 하위 X.
- **이유**: 환불은 결제와 *lifecycle이 다름*. 결제는 한 번 완료되면 종료, 환불은 *Payment 완료 이후 N회 누적*.
- **의존 방향**: `refund.domain`은 `payment.domain.Payment`를 **import하지 않는다**. 필요한 Payment 정보는 application 단에서 record로 주입.
- **장점**: refund 도메인을 *순수 POJO*로 유지 가능, 결제 모델 변경이 환불 도메인에 직접 전이 X.
- **거부한 옵션**: `payment.refund.*` 서브패키지. consistency.md zone은 같지만 lifecycle 분리 명확성을 위해 별도 컨텍스트 선택.
- **공유 자원**: `PortOnePaymentCancelPort`(application 포트)와 `ErrorCode`(common)는 결제와 공유.
- **함정**: refund.application이 payment.application의 내부 서비스를 직접 호출 → application 간 결합 증가. *공개 UseCase 포트만* 호출.
- **면접 가치**: "환불을 payment 하위로 둘지 별도로 둘지는 *lifecycle*이 기준이다. 같은 zone이라도 lifecycle이 다르면 컨텍스트는 분리한다."

## 16. *도메인 예외의 통일* — `BusinessException + ErrorCode`의 비용

`forbidden.md §4` + `errorhandling.md §1`의 통합 결정. 도메인별 Exception 클래스를 만들지 않는다.

- **거부한 옵션**: `RefundDomainException.of(ErrorCode)`. 도메인이 늘수록 *수십 개 Exception 클래스* 양산.
- **채택**: `throw new BusinessException(ErrorCode.REFUND_QUANTITY_EXCEEDED)`. 단일 타입에 ErrorCode로 의미 분기.
- **ErrorCode 자리**: `common.exception.ErrorCode`에 `// ─── 환불 ───` 섹션 추가. RF001~RF003.
- **장점**: GlobalExceptionHandler가 *한 곳에서* 모든 비즈니스 예외를 처리. HTTP 매핑은 ErrorCode의 `status` 필드로 자동.
- **트레이드오프**: ErrorCode enum이 길어진다. 도메인 섹션 주석으로 시각적 분리.
- **`withDetail` 패턴**: 추가 정보가 필요하면 `BusinessException.withDetail(ErrorCode.X, "paymentId=" + id)`. 메시지 합성.
- **함정**: ErrorCode 없이 메시지 하드코딩 → SSOT 깨짐 → 응답 메시지가 코드마다 달라짐.
- **면접 가치**: "도메인별 예외 클래스를 새로 만들지 않는 이유는 *분기 비용 vs 표현력*의 절충이다. ErrorCode가 의미를 들고, 핸들러는 한 곳."

## 17. *명시적으로 거부한 옵션*

채택된 옵션과 *동등한 1급 시민*. 거부의 이유가 본 Product의 깊이.

- **거부**: 클라이언트가 환불 *금액을 직접 입력*. *서버 자동 산정*만 허용 (보안·정합성).
- **거부**: 환불 단위 = 금액. *주문상품 ID + 수량* 단위만.
- **거부**: 자동 환불(배송 지연·품절 시스템 트리거). 1차는 사용자 명시 요청만.
- **거부**: 환불 사유별 정책 분기. 사유는 *입력만 받고 분기 없음*.
- **거부**: 환불 승인 워크플로우(관리자 승인). 1차 제외.
- **거부**: PG 취소 실패 자동 재시도·보상 트랜잭션. *로그 + 알람*만.
- **거부**: 트랜잭션 안 외부 호출. 락 hold time 증가.
- **거부**: 도메인별 Exception 클래스(`RefundDomainException`). `BusinessException` 통일.
- **거부**: 200 OK + warning 응답. *202 Accepted*로 변경.
- **거부**: RF001 = 400. *409 Conflict*로 변경.
- **거부**: `Idempotency-Key` 헤더. 비즈 식별자 자연 형성.
- **거부**: 도메인 서비스가 모든 Refund 로드 후 자바 합산. *DB SUM 쿼리*.
- **거부**: `applyBreakdown` setter형. *생성 시 주입* 불변.
- **거부**: 분산 락. 단일 인스턴스 비관적 락만.
- **거부**: 환불 시점 OrderItem 조회 = 결제 시점 단가라고 *간주*. 1차 명시적 한계로 표기, 정식은 후속.
- **공통 원칙**: *지금 비용 vs 미래 가치의 의식적 절충*. 1차는 단순성 + 정합성 보장, 후속은 정밀성 + 자동화.

## 18. *ADR 카탈로그*

본문에 명시된 ADR + 추가 후보. 사용자 명시 시에만 작성.

- **ADR-R01**: 환불 트랜잭션 경계 — 선검증 / DB 커밋 / PG 호출 3단계 분리.
- **ADR-R02**: 복합결제 환불 비율 분리 정책 — `floor + 잔액 흡수`.
- **ADR-R03**: DB-PG 호출 순서 — 환불은 *DB 커밋 후 PG 호출*.
- **ADR-R04 (후보)**: Refund 별도 컨텍스트 결정 — payment.refund.* vs refund.*.
- **ADR-R05 (후보)**: 가격 스냅샷 도입 — 정식 PaymentItem 마이그레이션 시점.
- **ADR-R06 (후보)**: 적립 포인트 회수 정책 — 결제 정책 객체 공유 방식.
- **ADR-R07 (후보)**: PG 취소 실패 시 처리 정책 — 자동 재시도 도입 여부.
- **ADR-R08 (후보)**: 멱등 키 출처 — 비즈 식별자 채택 근거.
- **ADR-R09 (후보)**: 응답 코드 매핑 — 202 / 409의 선택 이유.
- **ADR-R10 (후보)**: 분산 락 도입 검토 — 다중 인스턴스 전환 시.
- **ADR-R11 (후보)**: 환불 도메인 이벤트 도입 — 1차 직접 호출 → 후속 이벤트 발행.
- **ADR-R12 (후보)**: 환불 자동 트리거 도입 — 배송 지연·품절 정책.

## 20. *면접 서사 후보*

5초 깊이 증명 문장. 각 문장은 *왜 그런 선택을 했는지*를 한 호흡에 담는다.

- > **"환불은 결제의 역연산이 아니다. 외부 호출과 트랜잭션 위상이 거울 대칭이며, 멱등 키 출처도 다르다."** — Product 정체성 1줄 증명.
- > **"DB 커밋 후 PG 호출 실패는 예외가 아니라 운영 이슈다. 그래서 응답이 202다."** — `errorhandling.md §6` + 응답 의미론을 한 문장에 묶음.
- > **"환불 멱등 키는 서버 채번이 아닌 비즈 식별자다. *우연히 두 번 누른 요청*과 *의도된 추가 환불*을 잔여 수량으로 구분한다."** — 멱등 출처 분류 + 누적 추적.
- > **"선검증은 비용 절감이고 race 차단은 트랜잭션 안 락+재계산이다. 둘은 다른 역할이다."** — `idempotency.md §4` S+ 패턴 본질.
- > **"비율 분리에서 끝수는 포인트가 흡수한다. 외부 자원은 안전한 쪽으로, 내부 자원이 끝수를 진다."** — 소수점 정책의 정당성.
- > **"잔여 수량은 상태가 아니라 누적값이다. 매번 SUM으로 계산하고, 잠그고, 다시 계산한다."** — 시간 차원 잔액의 본질.
- > **"적립률은 결제 정책 객체에서 빌려온다. 환불에 숫자를 두 번 적으면 영원히 어긋난다."** — SSOT 압축.
- > **"외부 멱등성은 외부 정합성만 보장한다. 내부 정합성은 우리가 잡는다."** — `idempotency.md §7` 한 호흡 증명.

## 22. *본인 진척도 기준 우선순위*

학습 비용 vs 가치 기준 4분류. 본인 진척도에 따라 어디에 시간을 쓸지 결정.

- **이미 익숙한 영역**: `BusinessException + ErrorCode` 패턴, `@Transactional` 기본, JPA 엔티티 + Repository 골격, ApiResponse 래퍼.
- **Product 단위로 처음 정리하면 가치 큰 영역**: 외부 호출과 트랜잭션의 위상 분리, 비관적 락 + 사전조회 + 재검증 3단 race 가드, 응답 코드 의미론(`200`/`202`/`409`/`403`)의 분리.
- **완전히 새로 학습 가치 큰 영역**: PortOne V2 부분취소 API + `requestKey` 멱등 보장, `floor + 잔액 흡수` 정책의 프로퍼티 기반 테스트, 누적 잔여 수량의 DB SUM + 락 결합.
- **면접에서 가장 강한 영역**: 결제와 환불의 호출 순서 비대칭 설명, 멱등 키 출처 분류(서버 채번 vs 비즈 식별자), 보상 흐름의 응답 코드 정당성.

## 23. *다음 행동 제안*

본 카탈로그 학습 후 즉시 이어갈 작업 5선.

1. `consistency.md §2` zone 매핑표에 *환불* 행을 다시 읽고, `Refund` / `Payment` / `Point` / `Inventory` 단일 트랜잭션 단위로 묶이는 *불변식*을 한 문장으로 적어본다.
2. `idempotency.md §2` 멱등 작업 카탈로그에서 환불 행을 직접 채워보고, *키 출처 / 감지 메커니즘 / 응답 정책 / 윈도우* 네 차원을 본 카탈로그 §10·§11·§13과 일치하는지 확인.
3. 결제 Product `PortOnePaymentCancelPort` 코드 위치(`payment/application/`)와 어댑터를 열어 *시그니처 확장 영향 범위*를 직접 grep으로 확인.
4. 결제 Product 적립률 상수 위치를 grep으로 찾고, 본 Product에서 *어떻게 공유할지* 한 줄로 메모.
5. `RefundAmountCalculator` 프로퍼티 기반 테스트를 먼저 작성한다(`pgRefundAmount + pointRefundAmount == totalRefund`). 구현 전에 테스트가 먼저 깊이를 박는다.

가장 깊이 있게 다룰 가치가 있는 3가지는 *(i) 결제와의 호출 순서 비대칭과 보상 응답 의미론*, *(ii) 멱등 키 출처 분류와 누적 잔여 수량의 race 가드*, *(iii) 비율 분리 산정과 가격 스냅샷의 시간 차원*이다. 본 Product는 c1oud_mall product 묶음에서 *결제의 거울 대칭이자 외부 보상 패턴의 표준 사례*에 해당한다.
